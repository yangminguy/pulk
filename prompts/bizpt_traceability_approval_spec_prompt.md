# 구현 프롬프트 — 비즈니스PT 매니저: 추적성 · 승인 게이트 리포트 · 근거 서술 체계

> 이 문서는 `pulk` 레포에서 작업하는 구현 에이전트에게 그대로 전달하는 기능 명세 프롬프트다.
> 시작 전에 `CLAUDE.md`의 Reading Order와 Development Rules를 따르고, 완료 시 `docs/TASKS.md`, `docs/HANDOFF.md`를 갱신한다.

## 0. 배경과 문제 정의

비즈니스PT 매니저(`apps/bizpt-manager`)는 CMO 영상 파이프라인(`video_room_projects` 상태머신, `packages/l5-core/src/functions/video-room/*`)의 사장님용 콘솔이다. 사장님은 **동시에 여러 콘텐츠를 기획·제작·아카이브·관리**한다. 현재 콘솔은 이 멀티 콘텐츠 운영을 지원하지 못한다. 구체적 문제:

1. **추적성 부재** — 제목·썸네일·원고·도입부·본론 등 모든 산출물이 "어떤 콘텐츠의 것인지" 표시가 없다. 제목 디벨롭, 썸네일 디벨롭, 원고 등 모든 구역이 동일한 문제를 가진다.
2. **뷰트랩 리서치 판정 불가** — 후보 판정 화면에서 벤치마킹 대상 영상의 썸네일이 안 보여서 어떤 영상인지 알 수 없다.
3. **산출물 카드가 raw JSON** — 프로젝트 상세의 산출물 카드(`key_content_draft`, `pulling_content_report` 등)가 코드 그대로 노출된다. 실제 어떤 과정이 진행 중인지 한국어로 읽을 수 없다.
4. **승인 게이트가 형식적** — 상태머신에 승인 status는 있으나, 승인 시점에 사장님이 검토할 **리포트(기획서)가 제시되지 않는다**. 예: 키 콘텐츠 기획이 끝나면 곧바로 풀링 리서치로 넘어가는 것처럼 보이고, 무엇을 근거로 승인하는지 알 수 없다.
5. **프로세스 자체의 누락** — 제목 디벨롭의 시드 생성 절차(동일 주제 유튜브 영상 2개 탐색 → 썸네일 문구↔제목 교차 치환)가 생략되어 있고, 문구 업그레이드·원고 작성의 **근거 서술**이 없다.

## 1. 관련 코드 위치 (정본)

- 콘솔 UI: `apps/bizpt-manager/src/app/page.tsx`, `src/lib/statuses.ts`, `src/lib/api.ts`

- 기획·리서치 로직: 같은 폴더의 `key-content-planning.ts`, `key-content-report.ts`, `key-content-draft.ts`, `viewtrap-research.ts`, `pulling-content-planning.ts`, `pulling-content-report.ts`
- 훅·원고 로직: `thumbnail-develop.ts`, `thumbnail-plan.ts`, `intro-writer.ts`, `logic-block-writers.ts`, `script-factory.ts`, `script-integrator.ts`, `script-material-pack.ts`
- API 게이트웨이: NocoBase `cmo:*` 액션 (`cmo:listProjects`, `cmo:getProject`, `cmo:approveStageGate`, `cmo:decideGate`)
- 방법론 정본: 콘솔 내 지식베이스 12문서 (각 화면의 "근거:" 표기와 동일 체계). **키 콘텐츠 선별 기준, 벤치마킹 판별 기준은 이 문서 체계에 이미 정의되어 있으므로 리포트 생성 시 해당 기준 항목을 그대로 인용할 것.**

기존 승인 status 6종은 이미 존재한다: `key_content_approval`, `pulling_content_set_approval`, `hook_draft_approval`, `script_approval`, `video_qa_approval`, `upload_approval`. **새 status를 만들지 말고 이 6개 게이트에 기능을 붙인다.**

## 2. 기능 요구사항

### FR-1. 콘텐츠 정체성(Content Identity) — 모든 산출물·모든 구역

모든 산출물(제목, 썸네일, 원고, 도입부, 본론, 훅, 리서치 리포트, 렌더 잡 등)은 어디에 표시되든 **소속 콘텐츠 식별 헤더**를 반드시 함께 표시한다.

- 식별 헤더 구성: 프로젝트 제목 + 키 콘텐츠 주제(확정된 경우 `key_content_choice`의 `key_topic_title`) + 프로젝트 ID 축약(8자) + 현재 단계 배지 + (썸네일 확정 시) 썸네일 미니 프리뷰.
- 적용 범위: 제목 디벨롭, 썸네일 디벨롭, 원고·도입부/본론, 뷰트랩 리서치, 벤치마크·수집, 업로드·캘린더, 자동초안 잡, 렌더 잡 — **콘솔의 모든 구역**. 특정 뷰만 고치고 끝내지 않는다.
- 여러 콘텐츠가 섞이는 목록 뷰에는 **콘텐츠별 필터/그룹핑**(드롭다운: 진행 중 프로젝트 목록)을 제공한다. 필터 선택 시 해당 콘텐츠의 산출물만 표시.
- 데이터 계약: 모든 산출물 카드 레코드에 `project_id`는 이미 있거나 추가하고, API 응답에 식별 헤더 구성에 필요한 필드(프로젝트 제목, 키 주제, 상태)를 join해서 내려준다. UI에서 별도 N+1 호출로 조립하지 않는다.

### FR-2. 뷰트랩 리서치 — 후보 판정에 영상 실물 정보 표시

후보 판정 UI의 각 후보 행은 다음을 반드시 표시한다:

- 영상 썸네일 이미지(클릭 시 원본 유튜브 링크 새 탭), 영상 제목, 채널명, 구독자 수, 조회수, 게시일, 성과도·기여도(뷰트랩 지표), 영상 길이.
- 썸네일은 유튜브 표준 URL(`https://i.ytimg.com/vi/{videoId}/hqdefault.jpg`)로 조립 가능하므로 videoId만 있으면 별도 저장 없이 렌더 가능. 리서치 산출물에 videoId를 반드시 보존한다.
- 판정(채택/제외) 버튼과 판정 사유 입력란을 후보 행 안에 둔다. 판정 사유는 산출물에 기록한다.

### FR-3. 산출물 카드 인간화 — 한국어 과정 서술이 기본, JSON은 접힘

프로젝트 상세의 산출물 카드는 raw JSON 대신 **한국어 요약 뷰**를 기본으로 렌더한다.

- 각 카드 타입(`pt_context`, `product_definition`, `key_content_report`, `key_content_choice`, `key_content_draft`, `pulling_content_report`, 이후 추가되는 훅/원고/렌더 카드 전부)에 대해 타입별 렌더러를 만든다: **이 단계에서 무엇을 했고, 핵심 결과가 무엇이고, 왜 그렇게 판단했는지** 2~5문장 + 핵심 필드 표.
- 카드 상단에 한국어 카드명(예: `key_content_choice` → "키 콘텐츠 주제 확정")을 표기하고, 원본 JSON은 `<details>` 접힘으로 유지(디버그용).
- 프로젝트 상세 상단에 **"지금 진행 중인 과정" 타임라인**을 추가한다: 완료된 단계 → 현재 단계(무엇을 하는 중인지 한국어 한 줄) → 다음 단계. `statuses.ts`의 한국어 매핑을 재사용하되, 현재 단계에는 실제 작업 서술(예: "뷰트랩에서 '미용실 유입' 키워드 후보 12건 수집 중")을 산출물/잡 상태에서 끌어와 표시한다.

### FR-4. 키 콘텐츠 기획 승인 게이트 — HTML 기획서 필수

`key_content_ideation`~`viewtrap_key_research` 완료 후, **풀링 리서치로 자동 진행하지 않는다**. `key_content_approval` 게이트에서 시스템은 **HTML 기획서**를 생성해 사장님에게 제시하고, 승인 전에는 `viewtrap_pulling_research`로 전이할 수 없도록 상태머신에서 강제한다.

기획서(HTML, 자기완결형 단일 파일) 필수 목차:

1. **키 콘텐츠 주제와 선별 이유** — 어떤 기준(지식베이스의 선별 기준 항목을 명시적으로 인용)으로 이 주제를 골랐는지, 후보 대비 비교 근거.
2. **벤치마킹 영상** — 썸네일 이미지, 제목, 채널, 구독자 수, 조회수, 게시일, 성과도·기여도, 링크. 왜 이 영상이 벤치마킹 기준(문서에 정의된 기준)에 부합하는지 서술.
3. **판매 논리** — 이 주제가 상품 판매로 이어지는 논리 전개(`applied_sales_logic`이 null로 남지 않도록 생성 단계에서 필수화).
4. **풀링 키워드 계획** — 이 키 콘텐츠를 받치기 위해 어떤 키워드로 풀링 콘텐츠를 찾아볼 것인지 목록 + 각 키워드 선정 이유. 사장님이 이 목록을 보고 승인/수정 지시한다.

기획서는 산출물 카드로 저장하고(타입 예: `key_content_plan_doc`), 승인 구역(FR-6)과 프로젝트 상세에서 인라인 렌더한다.

### FR-5. 풀링 콘텐츠 승인 게이트 — 리서치 리포트 제시 후 승인

풀링 리서치 산출물도 동일하게 HTML 리포트로 사장님에게 제시하고, `pulling_content_set_approval` 승인 전에는 훅 제작 단계(`thumbnail_pattern_extraction`)로 전이 불가. 리포트에는 선별된 풀링 콘텐츠 세트 각각의 영상 정보(FR-2와 동일 필드: 썸네일 포함)와 선별 이유, 키 콘텐츠와의 연결 논리를 담는다.

### FR-6. 승인 구역(Approval Center) 신설

사장님이 관여하는 지점은 정확히 6곳이다: **① 키 콘텐츠 기획 승인 ② 풀링 콘텐츠 승인 ③ 훅 승인 ④ 원고 승인 ⑤ 영상 승인 ⑥ 게시 승인.**

- 콘솔에 "✅ 승인 센터" 뷰를 신설한다(기존 '오늘' 뷰의 승인 큐를 확장·대체 가능). 승인 대기 항목만 모아서 보여주고, 각 항목을 펼치면 **해당 게이트의 리포트(기획서/리서치 리포트/훅 시안/원고/영상 QA 결과/업로드 초안)가 인라인으로 렌더**되어 그 자리에서 검토 → 승인/반려/수정요청까지 완료할 수 있다.
- 각 게이트에는 대응 리포트 산출물이 **반드시 존재**해야 하며, 리포트 없이 게이트에 도달하면 승인 버튼을 비활성화하고 "리포트 생성 대기"를 표시한다. 리포트 없는 "바로 승인"은 제거한다.
- 반려/수정요청 시 사유 입력을 받고(`cmo:decideGate`의 `needs_revision` + note 활용), 사유는 해당 단계 재작업 입력으로 전달한다.

### FR-7. 제목 디벨롭 — 시드 생성 절차 복원 + 업그레이드 근거 로그

제목 디벨롭은 다음 절차로 시작해야 한다(현재 생략됨):

1. 같은 주제의 다른 유튜브 영상 **2개**를 탐색해 확보한다(영상 정보는 FR-2 필드 전부 보존).
2. 그중 한 영상의 **썸네일에 적힌 문구를 제목 시드로**, 그 영상의 **제목을 썸네일 문구 시드로** 교차 치환하여 디벨롭의 출발점을 만든다.
3. 이후 8기법 디벨롭을 진행한다.

그리고 문구가 업그레이드되는 **모든 반복**에서: 이전 문구 → 변경 문구 → **왜 바꿨는지(적용 기법·근거)**를 버전 로그로 기록하고 UI에 타임라인으로 표시한다. 참조한 영상 2개는 썸네일 포함으로 디벨롭 화면 상단에 상시 표시한다. 썸네일 디벨롭도 동일한 버전 로그 체계를 적용한다.

### FR-8. 원고 — 도입부·본론의 근거 서술과 본론 노출

- **도입부**: 왜 이렇게 썼는지, 어떤 영상을 벤치마킹했는지(영상 정보 표시), 어떤 구조(도입부 구조 공식)를 따왔는지를 원고와 나란히 표시한다. `intro-writer.ts` 산출물에 근거 필드(벤치마킹 videoId, 구조명, 서술형 이유)를 필수화한다.
- **본론**: 현재 원고 구역에서 본론 내용이 보이지 않는다 — 본론 전문을 표시한다. 그리고 본론이 **정해진 워크플로우 안에서 에이전트가 어떤 리서치를 거쳐 어떻게 도출되었는지** 근거를 함께 기록·표시한다: 사용한 리서치 소스(문서/영상/검색 결과), 각 논리 블록(`logic-block-writers.ts`)이 어떤 소스에서 왔는지 블록 단위 매핑, 채택한 구조와 이유.
- 원고 승인 게이트(④)의 리포트는 이 근거 서술을 포함한 원고 전문이다.

### FR-9. 리서치 데이터 소싱 기준 — "필요한 데이터가 무엇인가"로 소스를 결정

리서치를 뷰트랩 사이트 중심으로 돌리지 않는다. **유튜브 검색이 리서치의 중심**이고, 데이터 종류별로 소스를 다음 기준표에 따라 선택한다. 이 기준표는 `viewtrap-research.ts` / `viewtrap-tools.ts` 계층에 소싱 라우터로 코드화한다.

| 필요한 데이터 | 소스 (정본) | 방법 |
|---|---|---|
| 성과도 · 기여도 | 유튜브 **검색결과 페이지의 뷰트랩 플러그인 오버레이** | 유튜브 검색 → 확장 프로그램이 표시하는 값을 크롤링. 키워드당 검색결과를 **대량으로**(상위 노출 전체) 수집하는 것이 기본 동작 |
| 영상 자체 데이터 (제목, videoId, 채널, 구독자, 조회수, 게시일, 길이, 썸네일) | **YouTube Data API** | `services/youtube` 자격증명 사용. 크롤링으로 얻지 말 것 — API가 더 정확하고 저렴 |
| 노출 확률, 키워드별 조회수 합계 등 뷰트랩 전용 집계 지표 | **뷰트랩 사이트** | 위 두 소스로 얻을 수 없는 지표만 뷰트랩 사이트에서 조회 |

- 우선순위 원칙: 같은 데이터를 여러 소스에서 얻을 수 있으면 **API > 플러그인 오버레이 크롤링 > 뷰트랩 사이트** 순으로 싼 소스를 쓴다.
- 플러그인 오버레이 수집분(성과도·기여도)과 API 수집분(영상 메타)은 videoId로 병합해 하나의 후보 레코드로 저장한다 — FR-2의 판정 UI가 이 병합 레코드를 그대로 렌더한다.
- 어떤 소스에서 언제 가져온 값인지(`source`, `fetched_at`)를 필드로 남긴다. 소스 불명 데이터는 리포트에 쓰지 않는다.

## 3. 데이터·아키텍처 규칙

- 근거(rationale)·영상 참조(videoId, 채널, 구독자, 조회수, 게시일, 성과도, 기여도)는 **생성 시점에 산출물 스키마의 필수 필드**로 만든다. UI에서 사후 추론하지 않는다. 스키마는 `types.ts` / `key-content-planning.schemas.ts` 체계에 추가하고 zod(또는 기존 검증 체계)로 검증한다.
- 도메인 로직(리포트 생성, 시드 치환 절차, 근거 필수화)은 `packages/l5-core`에 둔다. UI 플러그인·bizpt-manager에 도메인 로직 하드코딩 금지 (CLAUDE.md Forbidden 준수).
- HTML 리포트는 자기완결형(스타일 인라인, 썸네일은 유튜브 URL 참조)으로 생성해 산출물 카드로 저장하고, 콘솔에서는 sandbox iframe 또는 정화된 innerHTML로 렌더한다.
- 상태머신 변경: 각 승인 status 진입 시 대응 리포트 산출물 존재를 사전조건으로 검사하고, 승인 없이는 다음 status로 전이 불가(이미 게이트 구조가 있다면 리포트 존재 검사만 추가). `state-machine.ts` 유닛 테스트에 6개 게이트 전이 차단 케이스를 추가한다.

## 4. 수용 기준 (Acceptance Criteria)

0. (FR-9) 소싱 라우터 유닛 테스트: 성과도·기여도 요청 → 플러그인 오버레이 경로, 영상 메타 요청 → YouTube API 경로, 노출 확률·키워드 조회수 합계 요청 → 뷰트랩 사이트 경로로 각각 라우팅됨을 검증. 후보 레코드에 `source`/`fetched_at`가 항상 존재.

1. 콘솔의 어떤 구역에서든 임의의 산출물을 봤을 때, 스크롤 없이 그 산출물이 어떤 콘텐츠 소속인지(제목·키 주제·ID·단계) 식별할 수 있다. 프로젝트 2개 이상 동시 진행 상태로 검증한다.
2. 뷰트랩 후보 판정 화면에서 모든 후보의 썸네일·구독자·조회수·게시일·성과도·기여도가 보이고, 썸네일 클릭 시 유튜브 원본이 열린다.
3. 프로젝트 상세의 산출물 카드가 기본적으로 한국어 서술로 읽히고, "지금 어떤 과정이 진행 중인지" 한국어로 확인 가능하다. JSON은 접힘 상태로만 존재한다.
4. 키 콘텐츠 기획 완료 시 자동으로 풀링 리서치가 시작되지 않고, 4개 목차(선별 이유·벤치마킹 영상 실물 정보·판매 논리·풀링 키워드 계획)를 갖춘 HTML 기획서가 승인 센터에 뜬다. 승인 전 전진 시도는 실패한다.
5. 승인 센터에 6개 게이트 유형만 모이고, 각 항목에서 리포트 인라인 검토 → 승인/반려(사유 포함)가 한 화면에서 끝난다. 리포트 없는 게이트는 승인 불가.
6. 제목 디벨롭 이력에서 시드(교차 치환) 단계와 참조 영상 2개(썸네일 포함)가 확인되고, 모든 버전에 변경 이유가 붙어 있다.
7. 원고 화면에서 도입부·본론 전문과 각각의 벤치마킹 영상·구조·리서치 근거가 함께 보인다.
8. `pnpm` 워크스페이스 테스트 통과 + `state-machine.ts` 게이트 차단 테스트 신규 통과.

## 5. 구현 순서 제안

1. 스키마 확장(근거·영상 참조 필수 필드) + 상태머신 게이트 사전조건 — 이후 모든 것의 토대.

4. FR-3 카드 타입별 한국어 렌더러 + 진행 타임라인.

## 7. 에이전트 실행 지침 — 루프 엔지니어링 (Fable용)

이 명세를 구현하는 에이전트는 아래 루프 구조로 작업한다. **한 번에 다 만들고 끝내지 말고, FR 단위 루프를 돌려서 각 루프의 종료 조건을 수용 기준으로 못 박는다.**

### 7.1 전체 구조

```
탐색 패스 (1회)
  → FR 루프 × N (스키마/상태머신 → 리포트+승인센터 → 식별헤더 → 카드 인간화 → 소싱 라우터 → 디벨롭/원고)
      각 루프: 계획 → 구현 → 검증 → 자가 리뷰 → 기록
  → 통합 검증 패스 (1회)
  → 문서 갱신 패스 (1회)
```

### 7.2 탐색 패스 (구현 전, 수정 금지)

- `CLAUDE.md` Reading Order의 문서와 §1의 코드 파일을 실제로 읽는다. **읽지 않은 파일은 수정하지 않는다.**
- 이 명세의 가정(승인 status 6종 존재, `cmo:decideGate` 시그니처, 산출물 카드 스키마 등)을 코드에서 검증하고, 어긋나는 가정은 명세를 코드 현실에 맞춰 조정한 뒤 조정 내용을 작업 로그에 남긴다.
- 작업 계획을 태스크 목록으로 만들고 FR별로 파일 단위 변경 계획을 적는다.

### 7.3 FR 루프 (각 FR마다 반복)

1. **계획**: 이 FR의 수용 기준을 다시 읽고, 변경할 파일과 테스트를 나열한다.
2. **구현**: 도메인 로직은 `l5-core`, UI는 `bizpt-manager` — 경계를 어기는 순간 롤백하고 다시 배치한다.
3. **검증 루프**: 타입체크 + 해당 패키지 테스트를 돌리고, 실패하면 고치고 다시 돌린다. **초록이 될 때까지 반복**하되, 같은 실패가 3회 반복되면 접근을 바꾸거나 원인 분석을 작업 로그에 남기고 다음 판단을 한다(같은 시도를 4회째 반복하지 않는다).
4. **자가 리뷰**: 자신의 diff를 이 FR의 수용 기준에 하나씩 대조한다 — "이 기준을 지금 상태로 시연할 수 있는가?"에 아니오가 있으면 3으로 돌아간다. 특히 FR-1은 "모든 구역" 적용이 기준이므로, 적용 누락 뷰를 grep으로 스스로 찾아낸다.
5. **기록**: 완료한 FR, 남은 FR, 조정한 가정을 태스크 목록에 반영하고 다음 FR로.

### 7.4 통합 검증 패스

- 워크스페이스 전체 테스트 + 빌드.
- 수용 기준 0~8을 처음부터 끝까지 체크리스트로 재검증한다(FR 루프 중 통과했던 항목도 다시 — 뒤 FR이 앞 FR을 깨뜨렸을 수 있다).
- 시나리오 검증: 프로젝트 2개를 동시에 생성해 키 콘텐츠 기획 → 기획서 생성 → 승인 차단/통과 → 풀링 승인까지 게이트 흐름을 실제로 통과시켜 본다.

### 7.5 종료 조건과 금지

- 종료 조건: 수용 기준 전부 통과 + `docs/TASKS.md`·`docs/HANDOFF.md` 갱신 + 아키텍처 결정이 있었으면 `docs/DECISIONS.md` 기록. 이 세 가지가 안 됐으면 "완료"라고 보고하지 않는다.
- 금지: 수용 기준을 낮춰서 통과시키기, 테스트를 skip 처리해서 초록 만들기, 리포트 생성 실패 시 게이트를 그냥 열어주는 우회 코드, TODO 주석으로 기능 대체.
- 막히면: 막힌 지점·시도한 것·다음 선택지를 정리해 보고하고 멈춘다. 추측으로 도메인 규칙(선별 기준, 판매 논리 구조)을 지어내지 않는다 — 지식베이스 문서에서 찾아 인용한다.
