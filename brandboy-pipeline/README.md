# 브랜드 다큐 롱폼 파이프라인 V5

브랜드보이 수준의 화면 밀도를 반복 가능한 규칙으로 고정하되, **실제로 구현 가능한 범위로 자른** 파이프라인이다.

---

## 이 저장소의 세 가지 결정

### 1. 코드는 4개만 만든다

품질 기준은 낮추지 않는다. 다만 **코드로 만들 것과 에이전트가 할 일을 분리**한다.

| 담당 | 하는 일 | 이유 |
|---|---|---|
| **코드 (4개)** | `align` · `review` · `assemble` · `qc` | 영상이 바뀌어도 동일한 작업. 타임코드·클릭 UI·CapCut JSON은 AI가 못 함 |
| **에이전트** | 원본 조사, 비트 분할, 구간 검색, 후보 수집, 모션 제작 | 브랜드마다 달라지는 탐색·판단. CLI로 굳히면 예외 처리만 늘어남 |
| **사람** | 원고, 녹음, 파일럿 승인, 화면 선택, 마감 | 자동화하면 품질이 떨어지는 영역 |

이전 버전의 명령 12개는 실제로 만들면 절반이 껍데기가 된다. `ingest` `evidence` `plan` `harvest` `motion` `caption-pass` `sound-pass` `pilot`은 **에이전트 워크플로우**(`prompts/`)로 옮겼다.

### 2. 수치는 한 파일에만 있다

편집 기준 문서에 흩어져 있던 40여 개의 숫자를 **`config/edit-profile.json`** 하나로 모았다.

**코드에 숫자를 하드코딩하지 않는다.** 기준 영상을 실측한 뒤 이 파일만 고치면 전체 검증 기준이 바뀐다.

### 3. 사전 검증을 통과하기 전에 구현하지 않는다

Whisper 단어 타임스탬프, CapCut 초안 열림, 알파 렌더 — 이 셋은 **파이프라인의 절반이 딛고 선 가정**이다. `spec/00-preflight.md`를 먼저 실행한다. 각각 대안이 준비돼 있으므로 실패해도 멈추지 않지만, **어느 경로로 갈지는 지금 정해야 한다.**

## 읽는 순서

### 구현하는 경우

1. `QUICKSTART.md` — 사전 검증 3종
2. `TASKS.md` — 구현 순서와 완료 조건
3. `docs/IMPLEMENTATION.md` — 아키텍처와 공통 규약
4. `schema/pipeline.ts` — 데이터 계약 (그대로 복사해서 시작)
5. `spec/00`~`08` — 모듈별 계약

**편집 기준 문서(`docs/craft/`)는 코딩할 때 읽지 않는다.** 필요한 수치는 전부 `config/edit-profile.json`에 있다.

### 영상을 만드는 경우

1. `docs/RUNBOOK.md` — 한 편 제작 순서
2. `docs/craft/EDITING-BIBLE.md` — 컷·샷 문법
3. `docs/craft/CAPTION-BIBLE.md` — 자막 5종
4. `docs/craft/SOURCE-PLAYBOOK.md` — 소스 수급
5. `docs/craft/SOUND-BIBLE.md` — 내레이션·원본음·음악

---

## 완성의 정의

네 조건을 동시에 만족해야 한다.

1. 원고만 들어도 공감 → 정보 → 관점 → 결론이 선명하다
2. 중요한 명사·동사·숫자가 바뀔 때 화면도 바뀐다
3. 모든 외부 화면이 원본과 사용 구간으로 역추적된다
4. 자막·진행자·원본음·음악이 하나의 리듬으로 움직인다

**CapCut 초안이 열리는 것은 완료 조건이 아니다.**
