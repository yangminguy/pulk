왜 이 방식이 안전한가: 신규 작업의 ~70%가 새 파일(타입·로직·UI 카드)이라 기존 라이브 코드와 충돌면이 작다. 상태머신·DB 스키마 무변경. 8단계 LLM은 기존 key-content-draft.ts의 "LLM 주입 + retry + 결정론 폴백" 패턴을 그대로 복제 → 검증된 레일.

② 어떻게 굴리나 — CTO → ACR Work Order 분해

이 작업의 정본 business는 #6 (repo = pulk 자체)다. 따라서 새 격리 repo가 아니라 pulk repo 위에서 ACR worktree 격리로 실행한다. 핵심 리스크는 미커밋 CMO/video-room WIP 파일 불가침(rule 00-global) — ACR이 이를 건드리면 안 된다.

⚠ WIP 충돌 가드 (필수 선행): 현재 pulk에 미커밋 변경 다수(script-room-types.ts, docs 등). ACR dispatch 전에 ① 작업 대상 외 WIP를 커밋 또는 stash하거나 ② Work Order allowedFiles를 신규 파일 + 명시 파일로만 화이트리스트. worktree 정책상 base branch 직접 수정은 차단되지만, dirty cwd는 과거 실험에서 409 "uncommitted changes"로 phase 전체를 막았다(직전 실험 핵심 실패 원인).

새로 주시할 오류 (이번 작업 특이)

  • 409 dirty cwd — WIP 미정리 시 phase 전체 차단. dispatch 전 stash/커밋으로 선제 차단.
  • dist 패치 누락 — plugin src만 고치고 dist 미반영 시 라이브 무변화(메모리: dist/plugin.js 직접 패치 필수).
  • LLM 결정론 폴백 무한 — 8단계 LLM이 매번 폴백으로 빠지면 "통과처럼 보이나 빈약". progress 카드의 실 LLM 호출 횟수로 검증.
  • 도메인 로직 UI 누수 — WO-4에서 점수 계산·검증을 카드에 하드코딩하면 rule 위반(l5-core로 회수).

④ 실행 순서 (승인 후)

  1. WIP 정리 — 작업 무관 미커밋 변경 stash/커밋 (409 선제 차단).
  2. CTO에 PRD dispatch — cto:planMessage로 4개 WO 의존 그래프 생성 → approvePlan.
  3. WO-1 먼저 단독 실행 — 가장 안전(순수+테스트). 여기서 NO-SKIP·과분해 차단 실작동을 먼저 관측.
  4. 모니터링 루프 — task 상태·execution-logs·큐를 폴링하며 phase별 exit/changed_files 기록, 개선 지표 대조.
  5. WO-2→3→4 순차 — WO-3에서 integrate phase 고립 판정 집중 관측.
  6. 완료 게이트 — l5-core jest GREEN + founder-ui build + Playwright smoke + 라이브 액션 401/200 확인 후 done 선언(rule 40 "agent says done ≠ done").
이 실험의 이중 목적: ⑴ CMO 제목 디벨롭 기능을 실제 구현하고, ⑵ 그 과정에서 직전에 코드로만 박아둔 CTO/ACR 개선(NO-SKIP / integrate phase / 과분해 차단 M9.8)이 라이브에서 실작동하는지 검증한다. 기능 산출물과 파이프라인 개선 검증을 한 번에 회수.
