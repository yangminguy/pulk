## 후보별 상세 분석

### A. 순수 React 커스텀 테이블

**개요**: `<table>` + `useState` + Joinery CSS 토큰으로 편집 가능 테이블을 처음부터 직접 구현.

**장점**
- 의존성 제로 — 프로젝트 의존성 극소화 컨벤션에 완벽 부합
- Joinery 디자인 시스템 네이티브 적용 (CSS 변수 직접 사용)
- 기존 founder-ui 컴포넌트(ApprovalCard, AgentLiveCard)와 동일한 패턴
- 번들 크기 증가 없음

**단점**
- 편집, 정렬, 필터, 행 추가/삭제, 유효성 검증 등 **모든 기능을 직접 구현**해야 함
- 열이 5개 이상이면 상태 관리 복잡도 급상승 (셀별 편집 모드, 포커스, 키보드 네비게이션)
- 테이블 기능 하나 추가될 때마다 코드량 선형 증가 — 유지보수 부담
- 대량 행 렌더링 시 가상화를 직접 구현하거나 별도 라이브러리 필요

**적합 시나리오**: 열 3-4개, 행 20개 이하의 단순 입력 폼 (사실상 폼 리스트)

---

### B. TanStack Table v8 (구 React Table)

**개요**: headless 테이블 라이브러리. UI를 전혀 제공하지 않고 **상태 관리·정렬·필터·페이지네이션 로직만** 제공. 마크업과 스타일은 100% 개발자가 제어.

**장점**
- headless → Joinery 디자인 시스템과 **충돌 없이 완벽 통합** 가능
- 정렬, 필터, 페이지네이션, 열 리사이즈, 고정열 등 테이블 코어 로직 검증 완료
- 번들 ~14KB — founder-ui 전체 의존성 대비 미미
- TypeScript 네이티브 (제네릭 기반 타입 추론)
- React 18 완벽 호환, SSR 지원
- 커뮤니티 대형 (GitHub 26k+ stars, 주간 2M+ npm 다운로드)
- 편집 기능은 직접 구현하지만, 테이블 구조(열 정의, 행 모델, 상태)는 프레임워크가 관리

**단점**
- 셀 편집(inline editing)은 직접 구현해야 함 — 단, 열 정의 기반이라 패턴화 용이
- 의존성 1개 추가 (`@tanstack/react-table`) — 극소화 컨벤션에서 판단 필요
- headless 개념 학습 비용 (createColumnHelper, flexRender 등)
- 복사/붙여넣기 스프레드시트 경험은 직접 구현

**적합 시나리오**: 열 5-15개, 행 수십~수백 개, 정렬/필터 필요, Joinery 스타일 유지 필수

---

### C. AG Grid Community

**개요**: 엔터프라이즈급 풀 피처 데이터 그리드. 편집, 정렬, 필터, 그룹핑, 가상화, 복사/붙여넣기 등 모든 기능 빌트인.

**장점**
- 편집 가능 테이블의 **모든 기능이 즉시 사용 가능** (셀 편집, 드롭다운, 날짜 피커, 유효성 검증)
- 대량 데이터 처리 (수만 행) 성능 최적화 완료
- 스프레드시트급 UX (범위 선택, 복사/붙여넣기, 키보드 네비게이션)
- Community Edition = MIT 라이선스

**단점**
- **번들 300KB+** — 현재 founder-ui 전체 프로덕션 의존성(next+react+react-dom)보다 클 수 있음
- **자체 CSS 필수** — Joinery 디자인 시스템과 시각적 충돌, 커스터마이징에 상당한 CSS 오버라이드 필요
- AG Grid DOM 구조가 고정 → Joinery 컴포넌트(`j-card`, `j-badge` 등) 내부 배치 어려움
- 프로젝트 컨벤션(의존성 극소화, 인라인 React)과 **정면 충돌**
- 리서치 입력 수준(열 5-10개, 행 수십 개)에 과잉 스펙
- 엔터프라이즈 기능(피벗, 차트, 서버사이드 행 모델)은 유료 — 기능 경계 혼동 가능

**적합 시나리오**: 열 20개+, 행 수천 개, 스프레드시트 대체가 목표인 경우

## 채택 권고: B. TanStack Table v8

### 근거

| 판단 기준 | 결론 |
|-----------|------|
| **Joinery 통합** | headless라 마크업 100% 제어 → Joinery CSS 변수 직접 적용 가능. AG Grid처럼 CSS 충돌 없음 |
| **의존성 정책** | 14KB 단일 패키지 추가. AG Grid(300KB+)과 달리 프로젝트 경량 컨벤션 유지 |
| **기능 대비 복잡도** | 커스텀(A)은 모든 로직 자체 구현으로 유지보수 폭발. TanStack은 테이블 코어(정렬/필터/페이지네이션/열 모델)를 위임하고 편집 UI만 직접 구현 — **적정 분업** |
| **확장성** | 향후 열/행 증가 시 가상화(`@tanstack/react-virtual`), 열 고정, 리사이즈 등 점진 추가 가능 |
| **MVP 원칙** | "PMF 신호 전 도구 금지" — 최소 의존성으로 빠르게 검증, 과잉 투자 방지 |

### 배제 근거

| 후보 | 배제 이유 |
|------|-----------|
| **A. 순수 커스텀** | 열 5개 이상의 편집 테이블에서 상태 관리·키보드 네비게이션·정렬 등을 모두 직접 구현하면 **코드량 대비 가치가 낮음**. 단순 폼이면 테이블이 아니라 카드 리스트로 충분 |
| **C. AG Grid** | 300KB+ 번들 + 자체 CSS = Joinery 디자인 시스템 파괴. 리서치 입력 규모(열 10개 미만, 행 수십 개)에 **엔터프라이즈 그리드는 과잉**. 프로젝트 의존성 컨벤션과 정면 충돌 |

### 구현 시 유의사항 (참고용, 이 문서는 분석만)

1. `@tanstack/react-table` 단일 패키지만 추가 (react-virtual은 행 100+ 넘을 때만)
2. `columnHelper.accessor()` + Joinery `<input>` 조합으로 인라인 편집
3. 기존 `globals.css` Joinery 토큰(`--paper-*`, `--ink-*`, `--space-*`) 재사용
4. 행 추가/삭제는 React state로 관리, API 저장은 기존 `lib/api.ts` 패턴 따름
