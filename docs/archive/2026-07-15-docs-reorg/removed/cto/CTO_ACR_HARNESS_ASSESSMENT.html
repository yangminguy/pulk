! 한 줄 결론

PRD 전체를 다 만든 것은 아닙니다. pulk 측 Phase 1(설계)·Phase 2(판단 계약/순수함수)는 완료, 이번 턴에 그 판단 로직을 라이브 dispatch 경로에 처음으로 연결했습니다. 하지만 실제 실행 커널(ExecutionRun/TeamRun API, Worktree, Verification, 병렬 실행)은 ACR 저장소 책임으로 아직 미구현입니다. 즉 "두뇌(판단)는 라이브, 손발(실행 안전장치)은 계약만" 상태입니다.

3 이전 대비 — 뭐가, 얼마나 나아졌나

BEFORE (이전 파이프라인)

  • CTO가 ACRIntent{phases}만 생성 → 단일 에이전트 dispatch
  • 복잡도·경계·금지파일 개념이 intent에 없음
  • cto-harness 순수함수는 존재하나 dispatch에 미연결 (선반 위 라이브러리)
  • 위험 파일(.env/lockfile) 하드블록 강제 없음
  • Control Room: status·CLI·branch·changed_files는 표시하나 복잡도 축 부재

AFTER (이번 턴)

  • dispatch 직전 applyHarnessMetadata()로 복잡도+모드+금지파일 부착
  • ACRIntent에 complexity / harness_mode / blocked_files 추가(하위호환 additive)
  • 판단 로직이 라이브 경로에 처음 연결됨 (선반 → 배선)
  • DEFAULT_BLOCKED(.env·lockfile·node_modules) 모든 dispatch에 하드블록
  • Control Room ComplexityBadge(C0~C5)로 복잡도 가시화
CTO(cto.ts): taskClass → complexity 판단 → applyHarnessMetadata → ACRIntent{complexity, blocked_files, harness_mode, ...} → POST /api/workbench/dispatch ACR(별도 repo): 지시대로 격리·실행, exec record에 complexity echo → control-room tree(complexity 패스스루) → ComplexityBadge

정량화(정직하게): 이번 턴의 핵심 델타는 기능 개수가 아니라 "판단 → 실행 계약의 연결 상태"입니다. ACRIntent가 싣는 안전 신호: 0개 → 4개(complexity·mode·blocked_files·requires_approval). 신규 테스트 스위트 1개(어댑터) 포함 l5-core 236건 그린. 그러나 end-to-end 라이브 실행으로 검증된 것은 아직 0건(ACR 측 수신부 미구현).

5 에이전트 팀 — 충분히 활용 중인가

2-Level 팀 오케스트레이션 설계 A · 라이브 F
Claude Code/Codex/Antigravity 역할분담, PRD 분해, 병렬 가능성 판단(canParallelize)까지 순수함수로 완성. 그러나 실제로 팀을 띄워 본 적이 없습니다 — /api/team-runs도, 병렬 ExecutionRun도, 실 result 수집도 미구현. 현재 라이브 dispatch는 여전히 단일 에이전트 경로.
  • 가드레일은 견고: C0/C1 team 금지, C5만 parallel, reason 없는 team rejected — 과잉 팀 사용을 코드가 막음.
  • 그러나 미연결: 이번 턴 라이브 배선은 taskClassToComplexity → applyHarnessMetadata까지. decomposeLargePRDToPackages→team-run은 cto.ts dispatch에 호출되지 않음.
  • 결과: 큰 PRD가 와도 지금은 단일 intent로 나감. 팀 분해는 "쓸 수 있는데 안 쓰는" 상태.

6 Hook · Command · Skill 활용도

🪝 Hooks 부분

pulk 개발 세션엔 PreToolUse 힌트 hook이 동작 중(이 세션에서도 관찰됨). 그러나 ACR 실행 런(run)에는 hook이 배선돼 있지 않음. Command Guard/Boundary를 PreToolUse hook으로 ACR 실행에 강제하면 가장 자연스러운 enforce 지점이 되는데 미활용.

⌨️ Commands 구조적 미활용

슬래시 커맨드는 인터랙티브 전용이라 헤드리스 ACR(claude/codex/agy)에서 못 씀(메모리 l5-cli-headless-vs-interactive). 대체재로 prompt-builder 9블록이 그 역할을 함 — 합리적이나, /code-review·/verify 같은 검증 커맨드의 가치를 프롬프트 블록으로 복제해야 동등해짐.

🧩 Skills 미연동

프로젝트에 validation-gate·build-one-slice·handoff-summary 등 풍부. 그러나 cto-harness 파이프라인이 이들을 직접 호출하지 않음. Verification/Handoff 단계를 기존 skill로 위임하면 중복 구현을 줄일 수 있음.

🤖 Subagent/Workflow 미활용

팀 분해를 Claude Code 네이티브 Agent/Workflow로 실행할 수 있는데, 현재는 자체 ACR 러너만 가정. OMC team/ultrawork 등 기존 병렬 실행기도 미연동.

7 더 나아지기 위한 남은 단계 (우선순위)

  1. ACR /api/execution-runs + /result thin adapter — 기존 runner 위에 얇게. 단일 run부터 end-to-end 라이브 검증. ACR repo
  2. Command Guard / Boundary Check를 실행 직전 enforce — ACR PreToolUse hook 또는 diff 검사로 boundary_violation 실제 발생시키기. ACR + hook
  3. Verification Layer 실 러너 — typecheck/build 기본, C2+ test, UI Playwright smoke. ACR repo
  4. /api/team-runs 라이브 — decomposeLargePRDToPackages 결과를 다중 run으로, dependency 순서 반영, result-aggregator 실수집·conflict detection. ACR + cto.ts 배선
  5. Control Room 통합 완성 — history / log tail / retry·review / team summary (현재 complexity badge만). founder-ui
  6. 기존 Skill/Workflow 위임 — Verification→validation-gate, Handoff→handoff-summary 재사용으로 중복 제거. pulk
  7. 이번 변경분 분리 커밋 — cto-harness/ · acr-intent.ts · cto-control-room · agents/cto.ts · founder-ui 2파일만 선택 add (CMO 미커밋분 제외). git
