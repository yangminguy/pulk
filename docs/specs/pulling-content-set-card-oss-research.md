# 오픈소스 조사: Pulling Content Set Card (5개 구조)

> 조사일: 2026-06-04

## 요구사항 요약

Pulling Content Set Card(끌어당기는 콘텐츠 세트 카드)는 CMO가 기획한 5개 구조(예: Hook, Problem, Solution, Benefit, CTA 등)의 인바운드/마케팅 콘텐츠 세트를 구조화된 카드 형태로 표시하고, 필요시 Founder가 직접 편집할 수 있는 UI 컴포넌트다.

| # | 요구사항 | 비고 |
|---|---------|------|
| 1 | 5개 구조 필드 표시 | 읽기 전용 뷰 + 편집 모드 토글 |
| 2 | 인라인 편집 (textarea / input) | 각 구조별 텍스트 편집 |
| 3 | 기존 디자인 시스템 일관성 | inline style + CSS 변수 (`j-card`, `var(--ink-1)` 등) |
| 4 | 모바일 반응형 | 기존 MobileShell 내 렌더링 |

## 도메인 1: UI 컴포넌트 라이브러리 (레이아웃/카드)

| 기준 | 자체 구현 (기존 패턴) | shadcn/ui (Radix 기반) | MUI (Material-UI) |
|------|---------------------|----------------------|-------------------|
| **라이선스** | — | MIT | MIT |
| **번들 크기** | 0 | ~15-30kB | ~100kB+ |
| **스타일 방식** | inline style + CSS 변수 | Tailwind utility class | Emotion / styled-components |
| **기존 패턴 호환** | ✅ 완전 호환 | ❌ Tailwind 미사용으로 충돌 | ❌ 스타일 시스템 완전 충돌 |
| **채택 근거 / 배제 이유** | 프로젝트 표준(BusinessContextSnapshotCard 등)과 일치. | 이 카드를 위해 Tailwind를 전역 도입하는 것은 과잉. | 무겁고 기존 CSS 변수 패턴과 융합이 어려움. |

### 채택: **자체 구현 (기존 inline style 패턴)**
- 프로젝트의 기존 모든 카드가 inline style + CSS 변수 패턴을 사용 중임.
- 5개 섹션을 나누는 단순한 UI이므로 외부 컴포넌트 도입 대비 이점이 없음.

## 도메인 2: 폼 관리 라이브러리

| 기준 | 자체 구현 (useState) | react-hook-form v7 | Formik v2 |
|------|---------------------|-------------------|-----------|
| **라이선스** | — | MIT | Apache 2.0 |
| **번들 크기** | 0 | ~9kB | ~13kB |
| **필드 수 대비 이점** | 5개 필드에 최적 | 10+ 필드, 복잡한 검증 시 유리 | 10+ 필드 시 유리 |
| **채택 근거 / 배제 이유** | 기존 ConsultationCard와 동일 패턴. 상태 관리가 단순함. | 5개 필드 폼에는 보일러플레이트가 더 큼. | react-hook-form과 동일한 이유로 배제. |

### 채택: **자체 구현 (useState)**
- 5개 구조(필드)는 `useState` 로컬 상태만으로 충분히 관리 가능함.
- 복잡한 유효성 검사(Validation) 요구사항이 없으므로 외부 라이브러리 불필요.

## 도메인 3: 드래그 앤 드롭 (구조 순서 변경) - *필요 시*

5개 구조의 순서를 편집(Reordering)해야 할 경우를 대비한 검토.

| 기준 | dnd-kit | react-beautiful-dnd | 자체 구현 (HTML5 DnD) |
|------|---------|---------------------|---------------------|
| **라이선스** | MIT | Apache 2.0 | — |
| **번들 크기** | ~10-15kB | ~30kB | 0 |
| **유지보수 상태**| 활발함 | Deprecated (유지보수 중단) | — |
| **채택 근거 / 배제 이유**| 모바일 터치 지원, 가벼운 번들, 확장성 좋음. | 더 이상 업데이트되지 않아 보안/버그 취약. | 모바일 터치 이벤트 처리가 매우 복잡함. |

### 채택: **dnd-kit (순서 변경 기능 포함 시)**
- 만약 5개 구조의 순서를 Founder가 자유롭게 변경해야 한다면, 모바일 터치를 완벽히 지원하고 번들이 가벼운 `dnd-kit`을 채택.
- 단순 텍스트 수정만 필요하다면 이 도메인은 도입을 보류(Deferred)함.

## 도메인 4: 리치 텍스트 편집기

| 기준 | 일반 textarea | Tiptap v2 | Lexical |
|------|---------------|-----------|---------|
| **라이선스** | — | MIT | MIT |
| **번들 크기** | 0 | ~150kB+ | ~50kB |
| **채택 근거 / 배제 이유**| plain text 입력에 적합. 가벼움. | 서식 편집 불필요. 오버스펙. | Tiptap과 동일한 이유로 배제. |

### 채택: **일반 textarea**
- 구조별 내용이 1~3문장 수준의 평문(plain text)이므로, 기존 패턴대로 `textarea` 사용이 가장 합리적.

## 종합 결론

| 도메인 | 채택 | 배제 (이유) | 번들 추가 | 통합 시점 |
|--------|------|-------------|-----------|-----------|
| UI 레이아웃 | **자체 구현** | shadcn/ui (스타일 충돌), MUI (과잉/충돌) | 0 | 카드 구현 시 |
| 폼 관리 | **useState** | react-hook-form (5필드에 과잉) | 0 | 카드 구현 시 |
| 순서 변경(DnD) | **dnd-kit** (조건부) | react-beautiful-dnd (지원 중단) | ~15kB | 순서 편집 기능 필요 시 |
| 텍스트 편집 | **textarea** | Tiptap, Lexical (과잉) | 0 | 카드 구현 시 |

**최종 채택 근거:**
단순 5개 구조 텍스트의 조회 및 편집을 위한 카드이므로, 기존 프로젝트 패턴(자체 UI + `useState` + `textarea`)을 유지하여 의존성을 최소화한다. 단, "5개 구조의 순서 조정(Sortable)"이 핵심 요구사항으로 확정될 경우, 모바일 호환성이 뛰어난 **dnd-kit**만 예외적으로 도입한다.
