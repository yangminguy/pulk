1Executive Summary

펄크는 특정 업무 하나를 자동화하는 도구가 아니라, 창업자가 새로운 사업을 계속 만들고 실험하며 운영하는 방식을 시스템화하는 AI 기반 회사 운영체계다. 일반 자동화 도구가 "입력된 업무를 더 빠르게" 처리하는 데 집중한다면, 펄크는 "무엇을·왜 해야 하는가, 누가 어떤 기준으로 판단하는가, 어떤 실험을 거쳐 제품화하는가"까지 포함하는 상위 운영 구조를 지향한다.

핵심 가정은 창업자의 병목 제거다. 초기 사업가의 가장 큰 제약은 아이디어 부족이 아니라 실행의 지속성, 우선순위 판단, 검증 루프, 반복 개선, 학습 축적의 부재다. 펄크는 창업자가 모든 태스크를 직접 쪼개고 검수하는 구조에서 벗어나, CEO·Chief of Staff·CMO·CRO·CPO·CTO·COO·CFO·Risk/QA·Culture·Hermes로 구성된 AI 임직원 조직이 역할을 나눠 수행하도록 설계된다.

철학은 "No Demand → No Tool / Paid Demand → Productization"이다. 처음부터 거대한 SaaS를 만들지 않는다. 콘텐츠·메시지·인터뷰·랜딩·DM·수동 운영으로 먼저 수요를 검증하고, 반복 워크플로우가 확인될 때만 도구화한다.

1.1 최상위 판단 (갱신)

제품 카테고리펄크의 최상위 카테고리는 AI Business OS / Founder Operating System이다. 개발툴이 아니다.
실행 엔진ACR(Agent Control Tower)은 펄크 전체가 아니라 CTO의 실행 하위 엔진이었고, 현재는 2단계 Native Orchestration으로 정리되었다. pulk CTO는 "판단"만, native 오케스트레이터가 worktree·phase·verify·merge를 소유한다.
Shell 전략NocoBase + PostgreSQL을 MVP Shell/Agent 작업장으로 쓰되, 핵심 로직은 l5-core로 분리한다. Founder-facing UX의 중심은 chat-first(founder-ui)다.
Hermes강한 감시자이자 운영 신경계이지만, 코드 수정·자기 승인·Release Gate 우회 권한은 없다.
자가개선Tiger 루프가 매일 병목을 수집·분석해 개선 카드를 만들고, Founder 일괄승인 후 CTO가 병렬로 고친다. 시스템이 스스로 진화한다.
첫 수익화펄크 자체 판매보다, 펄크를 이용해 작은 브랜드/로컬 사업자의 마케팅 자동화를 운영·상품화하는 것이 현실적. CMO 트랙이 그 첫 Business다.

전략적 결론

펄크 MVP는 "모든 기능이 있는 OS"가 아니라, Founder 입력 → CEO 해석 → 임원 병렬 실행 → Approval Queue → Hermes 감시 → Memory 저장 → 워크플로우 진화가 하나의 실제 Vertical Slice로 작동하는 것이다. 이 슬라이스는 이미 동작하며(Phase 1~5 완료), 이제 자동 브리핑·승인 라우팅·메모리 지속화로 완성 중이다(Phase 6).

2배경과 문제정의

펄크의 출발점은 "AI로 무엇을 자동화할 것인가"가 아니라 "창업자의 반복적 병목을 어떻게 시스템으로 제거할 것인가"다. 창업자는 아이디어가 많아도 실제로는 시장검증·고객 인터뷰·세일즈 메시지·콘텐츠 발행·개발 요청·QA·지표 확인·회고·다음 실험 설계를 모두 직접 챙긴다. 이 구조에서는 창업자의 체력과 집중력이 곧 회사의 처리량이 된다.

기존 업무관리툴은 태스크를 저장·표시하는 데 능하지만 생성 이유·사업적 우선순위·고객 반응 기반 수정·조직적 역할 분담을 자동 수행하지 못한다. 일반 AI 챗봇은 좋은 답을 주지만 장기 운영 메모리·실행 상태·승인 정책·PMF 실험판·조직 구조가 없다. 펄크는 이 둘 사이의 빈 공간을 채운다.

2.1 구체적 병목 (PRD 반영)

2.2 왜 지금인가

AI 도구가 늘수록 역설적으로 창업자의 관리 부담도 커진다. Claude Code·Codex·자동화 도구·문서 도구·DB·대시보드가 따로 움직이면 창업자는 다시 이 도구들의 PM이 되어야 한다. 펄크는 개별 도구를 더 많이 쓰는 것이 아니라, 이 도구들을 회사 운영체계 안에 배치·통제하는 상위 구조다. 초기 사용자는 창업자 본인이며, 본인의 사업 실험을 펄크 위에서 돌리며 반복되는 구조를 제품화한다.

3제품 정체성·핵심 원칙

펄크는 세 개념이 겹친다. ① Founder Operating System — 창업자의 의사결정 기준·성향·리스크 허용범위·브랜드 톤을 시스템에 반영. ② AI Company OS — AI를 어시스턴트가 아니라 역할·책임을 가진 임직원 조직으로 운영. ③ PMF Experiment Engine — 새 사업/상품을 수요 검증 중심으로 반복 실험. 셋을 묶으면 정체성은 "창업자의 사업 감각을 조직화된 AI 운영체계로 바꾸는 시스템"이다.

구분펄크가 아닌 것펄크가 지향하는 것
챗봇질문에 답하고 대화를 저장하는 비서대화를 실행 가능한 사업 가설·워크플로우로 변환하는 운영체계
업무관리툴사람이 입력·관리하는 보드AI가 태스크를 생성·배분·감시·회고하는 실행 시스템
자동화툴조건-액션을 잇는 Zapier류수요 검증 후 반복 워크플로우를 도구화하는 제품화 엔진
개발툴코드 생성/QA에 국한개발 실행도 포함하되 사업 운영 전체를 포괄하는 OS

3.1 핵심 원칙

Company Culture First

기능보다 운영 문화·의사결정 원칙을 먼저 정의. Culture 에이전트가 정렬성 검토.

Founder DNA as Default Context

창업자 기준은 매번 설명하지 않아도 기본 컨텍스트로 작동.

Generative Workflow

고정 템플릿만 쓰지 않고 사업 상황에 맞춰 워크플로우를 생성.

Small PMF Before Build

콘텐츠·메시지·인터뷰·랜딩으로 먼저 수요 확인.

No Demand, No Tool

반복 수요·유료 의사 확인 전에는 무거운 개발을 미룸.

Approval by Risk Level

위험도에 따라 자동 실행 / 검토 / 창업자 승인 구분.

Memory Compounding

모든 실행·판단은 다음 실행 품질을 높이는 메모리로 축적.

Chat-first, Shell-separate

Founder UX는 채팅. NocoBase는 Agent 작업장. 핵심 로직은 l5-core.

3.2 명명 규칙

Pulk = 브랜드명, L5 Business OS = 제품 카테고리/기술적 설명, AI Business OS = 일반명. 외부 소개는 "Pulk — AI Business OS for Founders", 내부 문서는 "L5 Business OS Architecture".

4L5 운영 루프

펄크 중심에는 L5 운영 루프가 있다: Sense → Think → Design → Execute → Measure → Learn → Evolve → Repeat. 창업자가 아이디어를 입력하면 시스템은 단순히 답하지 않고, 맥락을 감지하고 사업성을 판단하고 실행흐름을 설계하고 임원을 배치하고 결과를 측정하고 배운 것을 다음 워크플로우에 반영한다. 자율성은 무조건 높이는 것이 아니라 위험도와 데이터 확실성에 따라 조절된다.

4.1 BPR 6-Phase 매핑

운영 루프는 사업 재설계 관점에서 6단계 phase로도 관리된다: ① Direction Alignment → ② Market/PMF Diagnosis → ③ Offer/Workflow Redesign → ④ Execution System Build → ⑤ Sales/Revenue Test → ⑥ Monitoring/Optimization(Scale·Automation). phase 전환은 승인 게이트를 가진다.

운영 원칙

펄크는 "아이디어 → 개발"이 아니라 "아이디어 → 작은 수요 검증 → 반복 워크플로우 발견 → 도구화 → 매출화" 순서로 움직인다.

5시스템 아키텍처 (현행)

펄크 아키텍처는 4개의 두뇌를 명확히 분리한다. 하나의 범용 AI에 모든 것을 맡기지 않고, 판단·실행·감시·자가개선을 서로 다른 시스템이 소유한다.

🧠 pulk CTO
판단(Brain)

요구사항 → task/spec/risk → complexity(C0~C5) → agent 배정 → Work Order. 코드는 직접 쓰지 않는다.

⚙️ Native Orchestration
실행(Executor)

2-level. worktree 격리 · 병렬 phase · verify gate · merge · e2e/QA를 소유.

🔔 Hermes
감시(Nervous System)

멈춤·실패·드리프트·승인대기 감지, Brief 생성, 개선 제안. 읽기 전용.

🐯 Tiger
자가개선(Self-Improve)

병목 수집 → Claude 분석 → 카드 → Founder 일괄승인 → CTO 병렬 실행 → 메모리 학습.

5.2 CTO 실행: 2단계 Native Orchestration (ACR → native 전환)

이전 기획서는 "Agent Control Tower(ACR)를 CTO가 호출한다"고 봤다. 현재는 ACR이 기획(분해)과 실행(Harness)을 동시에 하던 책임 분산을 정리하고, pulk CTO(판단) + Native Orchestration(실행)으로 분리했다. Native Orchestration이 worktree 격리·병렬 phase·verify gate를 이미 커버하므로 별도 Harness가 불필요해졌다.

Founder 요청 / 큰 PRD │ (pulk CTO 1차 분해 · decomposeLargePRDToPackages) ▼ Work Package[] + main agent 배정 (selectMainAgent → claude-code / codex / antigravity) │ (각 main agent 2차 오케스트레이션 · complexity 기반 · selectInternalOrchestrationMode) ▼ MainAgentWorkPackage (C0~C5 guardrail로 solo / sub-agent / sequential team / parallel team 결정) │ (Native Orchestration 실행) ▼ worktree 격리 → 병렬 phase → verify gate → merge → e2e → QA → TeamResultPacket 회수

관련 코드: packages/l5-core/src/functions/cto-native, cto-planning, cto-design, cto-verification, services/agent-runtime/src/orchestrator/. pulk는 task 상태만 관리하고, ExecutionRun(실행 시도)은 오케스트레이터가 소유한다.

5.3 Shell 분리 원칙

초기 구현에서 중요한 것은 NocoBase에 과도하게 종속되지 않는 것이다. NocoBase는 MVP Shell·Admin UI·Plugin Host·Agent 작업장으로 쓰고, 핵심 규칙·타입·의사결정 로직·워크플로우 모델은 l5-core에 둔다. 그래야 Next.js·자체 백엔드·다른 DB·SaaS 환경으로 이전해도 핵심 자산을 보존한다. Founder-facing 경험의 중심은 apps/founder-ui(Next.js) 채팅이다.

6.1 CEO ↔ Chief of Staff

CEO는 "무엇을·왜 해야 하는가"를, Chief of Staff는 "누가 언제 무엇을 어떻게 해야 하는가"를 담당한다. CEO는 대부분의 사업 판단을 하되 결제·법적 책임·고위험 외부 실행은 Founder 승인으로 남긴다. CEO Clarification Gate: 지시가 불충분하면 자동 분해하지 않고 채팅으로 되묻는다(needs_clarification).

6.2 FounderDeliverable 종합 신규

한 지시에서 파생된 모든 task가 종료(done/killed, ≥1 done)되면 Chief of Staff가 단일 종합 산출물을 만든다. 구조는 코드 소유(UNIQUE(instruction_id) 멱등 백스톱), 요약은 LLM + 결정론 규칙. 필드: decision_summary, contributions[](agent·task·요약·상태), next_actions[](approve/hold). 창업자는 임원별 산출을 일일이 읽지 않고 하나의 카드로 결정한다.

6.3 임원 간 위임 루프 (Executive Delegation) 신규

임원 A가 산출 도중 임원 B의 작업이 필요하면 CEO를 거쳐 위임하고, 자동 검증-수정 루프를 반복한다. 예: CMO가 영상 생성기 수정을 CTO에게 위임 → CTO 제작 → CMO가 acceptance_criteria 대비 검증 → fail이면 피드백 재투입 → pass 또는 예산소진까지 → 원래 CMO 작업 재개.

CMO tool-loop 중 ask_executive(to='CTO', objective, acceptance_criteria, max_rounds=3) ▼ CEO 게이트 (1회 정책 검토 — 고위험/아웃바운드면 Founder 승인 토큰) ▼ while round < max_rounds: ← CEO LLM 미개입, 결정론 제어 (비용 0) CTO 제작 → CMO 검증(체크리스트) → fail → 피드백 재투입 ▼ pass or 예산소진 → 원래 task 재개 | escalate_founder

안전장치: max_rounds(기본 3, 상한 5) · acceptance_criteria 필수(없으면 위임 거부) · 자기 위임 금지 · 승인 게이트 유지. 코드: l5-core/functions/delegation, consultation.

6.4 임원 = Claude Code 서브에이전트 + 멀티채널 신규

임원은 JSON만 뱉는 함수가 아니라 실제 작업이 가능한 서브에이전트다. 텔레그램 인바운드 게이트웨이(services/telegram-gateway)가 @ceo/@cto/@cmo 메시지를 파싱해 claude -p로 임원을 소환하고 결과·파일을 회신한다. Founder의 Mac에서 launchd(KeepAlive)로 상주. .claude/agents/는 팀 공유 설정으로 git 추적, .telegram-runs/는 무시.

6.5 Hermes 포지션

Hermes는 단순 알림봇보다 강한 운영 신경계이지만 중앙 CEO가 되어서는 안 된다. 멈춘 작업·오래된 승인·반복 실패·품질 저하·드리프트·지표 이상을 감지해 Founder/관련 Agent에 개입 요청을 보낸다. 그러나 위험 작업 자기 승인·코드 직접 수정·Release Gate 우회는 금지된다. (상세: §9 Tiger)

7위험도 × 복잡도 이원 체계

8핵심 모듈 상세

핵심 모듈은 독립 기능처럼 보이지만 하나의 운영 루프 안에서 연결된다.

8.1 Founder DNA Room

창업자의 성향·선호·판단 기준·사업 철학을 저장. 선호 시장, 피할 사업, 콘텐츠 톤, 가격 정책 성향, 리스크 허용범위, 승인 기준, 브랜드 감각, 업무 스타일. 카테고리: business_preference · risk_standard · strength · weakness · brand_tone · decision_rule, 각 항목 confidence(1~5). 기능: 사업 적합도 점수화, 스타일 일관성 검토, 승인/거절에서 새 선호 추출(자동 반영 아닌 업데이트 후보 제안), 경계 설정.

8.2 Business Portfolio (BusinessIdea → Business → Project) 계층 확장

구상/실행 중인 사업·실험·상품 후보를 관리. 3단계 계층으로 확장되었다.

레벨의미상태(status)

8.3 Workflow Factory

창업자의 추상적 입력("마케팅 자동화 상품을 만들자")을 실행 가능한 워크플로우로 변환하는 실행화 엔진. 입력: business idea + Founder DNA + culture + relevant memory + available agents + 제약. 자동 생성 문서: BUSINESS_BRIEF · FOUNDER_FIT_SCORE · OPPORTUNITY_SCORE · BUSINESS_MODEL_DRAFT · PMF_EXPERIMENT_PLAN · AGENT_STAFFING_PLAN · REVENUE/MARKETING/SALES/DELIVERY/BPR_WORKFLOW · TOOL_REQUESTS · 7_DAY_EXPERIMENT · KILL_OR_SCALE_CRITERIA. 규칙: PMF 실험은 도구 요청 전에, 도구 요청은 반복 신호(주 3회+) 필수, 워크플로우는 구조화 레코드로 저장.

8.4 PMF Experiment Board

펄크가 툴 개발에 빠지지 않게 막는 핵심 장치. 시장 반응을 먼저 본다. format: content · message · landing · proposal · manual_delivery · interview · waitlist · survey, pmf_score, signal_level(1~5). 설계 요소: Customer Segment / Pain Point / Offer / Channel / Signal / Threshold / Learning.

8.5 Decision Queue · Approval Gate

시스템이 Founder에게 결정을 요청하는 대기열. 모든 것을 묻는 시스템은 자동화가 아니고, 아무것도 묻지 않는 시스템은 위험하다. decision_type: founder_approval / risk_review / tool_subscription / external_send / pricing / legal_financial, risk_level D1~D5, status: pending / approved / rejected / needs_revision. (§7 승인 정책과 연동)

8.6 Hermes Control Room · BPR · Tiger

Hermes가 감시하는 상태와 트리거를 보여준다: 멈춘 작업, 마감 지난 PMF 실험, 승인 필요 항목, 반복 업무 감지, BPR 제안, Tool Request 후보. BPR Room은 반복 병목·실패 원인을 분석해 프로세스를 재설계한다(Local/Company/Triggered BPR). 이 BPR 분석이 Tiger 자가개선 루프로 자동화되었다(§9).

8.7 Memory Room

결정·인사이트·워크플로우·고객 반응을 저장·재사용. 단순 노트가 아니라 재사용 가능한 운영 자산. 유형: Founder / Business / Customer Insight / Workflow / Decision / Failure Pattern / Risk Policy / Revenue Memory. AI 생성 메모리는 confidence·source와 함께 저장되고, PII 분리·큐레이션(§10)을 거친다.

8.8 Tool Request Lab

반복 업무·병목을 도구화 후보로 관리. 필드: 반복성, 소요 시간, 실수/누락 위험, 매출/PMF 영향, reuse_potential(1~5), cto_decision(manual_for_now / local_script / no_code_tool / internal_feature / native_orchestration / claude_code / codex / antigravity / hermes_automation / future_saas / reject). No Demand → No Tool 원칙의 집행 지점.

9Tiger 자가개선 루프 신규 핵심

호랑이(Tiger)는 펄크가 스스로 병목을 찾아 고치는 자가개선 신경계다. 이전 기획서의 "BPR Room" 개념이 매일 도는 자동 루프로 구현되었다.

1. [수집] cross-repo 수집기가 도구 레지스트리 순회 → 임원·도구·repo별 병목 후보 모음 2. [분석] Claude(호랑이 두뇌, night-BPR)가 후보 분석 → 개선 카드 작성 (D1~D2 자동) 3. [제안] founder-ui '🐯 자가개선' 사이드바에 카드 노출 (문제 / 근본원인 / 해결예정 / 대상 repo) 4. [승인] Founder가 카드 다중선택 → 일괄 승인 (단일 게이트) 5. [실행] CTO가 target_repo별 그룹핑(RepoGroup) → native-orchestrator 병렬 worktree → verify → merge 6. [학습] 결과(성공/실패) → MemoryEntry 적재 (category: bpr / failure) 7. [순환] 다음날 분석이 이 메모리를 입력으로 받아 품질 향상

도구 레지스트리

임원별 도구를 1줄로 등록(owner · 도구명 · repo_path · error_sources · manual_intake). 새 도구 = 레지스트리 한 줄 추가 → 수집·분석·디스패치 전 경로에 자동 편입.

수집 소스

(A) 자동 어댑터: jsonl 로그 / dir-scan / agent-tasks. (B) 수동 제보: Founder 텔레그램·UI. 외부 repo(영상 팩토리 등)도 포함.

호랑이 두뇌

night-bpr-loop.ts, Claude CLI 헤드리스 전담. 후보 → BPRLog(근본원인) + WorkflowImprovementProposal(카드). 과거 MemoryEntry를 입력으로 재발·회피·우선순위 반영. OpenAI 미사용.

CTO 병렬 실행

승인 카드를 target_repo별 RepoGroup으로 묶어 native-orchestrator 병렬 실행. 동시성 상한 max(1, cpu-2). 결과 merged/held/failed + 사유 → 메모리.

Tiger 스코프 = D1~D2 고정 · 금지사항

  • ✗ 외부 고객 발송·결제 자동화  ·  ✗ .env/.git/lockfile 수정  ·  ✗ DB schema 마이그레이션
  • 이런 항목은 코드로 고치지 않고 카드를 approval_required=true + risk_level=D4로 /approval 큐에 보낸다.

관련: l5-core/functions/tiger, bpr, services/hermes-runtime/src/tiger/(watchdog collector · liveness · recovery), founder-ui /self-improve. 실시간 장애 감시(~90s 지연) + 4회 자동복구 루프 실증.

10데이터·메모리·거버넌스

펄크의 장기 경쟁력은 데이터와 메모리에 있다. 매번 새 대화처럼 시작하면 운영체계가 아니라 일회성 비서다. 사업별 실행 기록·고객 반응·의사결정·실패 패턴·승인 사유·워크플로우 성과를 구조화 저장하고, Founder가 조회·백업·export할 수 있어야 한다.

10.2 메모리 큐레이션 신규

메모리는 무한정 쌓이지 않는다. curation_decision(auto_save / auto_discard / needs_review)과 discard_reason(pii_high / too_short / duplicate / low_value)로 분류되고, 폐기 항목은 purge_at(폐기 후 30일)에 cron 삭제된다. pii_level='high'는 LLM 컨텍스트로 전송되지 않는다.

10.3 거버넌스 원칙

  • Founder는 핵심 데이터에 대해 조회·백업·export 권한을 가진다.
  • 고객 PII(pii_level)와 비식별 인사이트(allowed_usage: internal_only / reusable_anonymized / restricted_customer_purpose)를 분리 저장.
  • AI 생성 메모리는 confidence·source를 함께 저장.
  • 중요한 Founder DNA 변경은 자동 반영이 아니라 업데이트 후보로 제안.
  • 승인 이력·고위험 실행 로그는 삭제하지 않고 감사 가능하게 보존.
  • MVP 단계에서도 데이터 모델은 이전 가능성을 고려해 NocoBase 종속을 낮춘다.

11.1 구현 원칙

  • 9개 플러그인을 한꺼번에 만들지 않는다. 하나의 실제 Vertical Slice를 먼저 완성한다.
  • NocoBase는 교체 가능한 Shell, 핵심 로직은 l5-core에.
  • Agent 실행보다 먼저 데이터 모델·승인정책·워크플로우 스키마를 안정화한다.
  • 개발 자동화는 CTO 하위 시스템으로 분리하고 Business OS와 혼동하지 않는다.
  • 결정론 우선: phase 생성은 classifyTask+템플릿, LLM은 opt-in 안전망.
  • "Agent says done" ≠ Done. 검증 통과 = Done. 유형별 검증(문서/API/UI/DB/runner/보안) 강제. 모든 scoring rule은 단위테스트 필수.
  • 로컬/무료/저비용 우선, 운영 안정화 시 관찰성·예약 실행 도구를 붙인다.

13첫 사업: 마케팅 자동화 (CMO 트랙)

펄크 자체를 바로 SaaS로 파는 것은 위험하다. 더 현실적인 전략은 펄크를 내부 운영체계로 써서 작은 브랜드/로컬 사업자의 마케팅 자동화라는 명확한 고객 문제를 먼저 푸는 것이다. 이것이 첫 Business이며, CMO 트랙으로 실제 집행되고 있다(§12.2). 사용자의 기존 관심사(릴스·블로그·숏츠·쓰레드 자동화, 작은 브랜드 성장, AI 수익화 상품)와 정확히 맞는다.

13.1 CMO v3 구조

video-room(25 stage, 509 tests, 도메인 순수 함수)이 source of truth이고, cmo-orchestrator는 스킬 선택·순서·승인 게이트 층(thin adapter). 각 AgentSkill은 video-room 순수 함수를 호출하는 5~15줄 어댑터로 중복 로직을 방지한다. YouTube 핫비디오·업로드·썸네일 레퍼런스, viewtrap 크롤링(사장님 in-app 검색 후 로드된 테이블만 읽는 human-in-loop) 포함.

14운영 정책·승인 게이트·리스크 관리

14.3 품질관리 정책

  • 모든 외부 산출물은 목적·대상·채널·리스크 레벨을 가진다.
  • 중요 결정은 recommendation만이 아니라 options·trade-off를 함께 제시한다.
  • 실험 결과는 숫자 지표와 정성 인사이트를 분리 저장한다.
  • 자동화 실패는 숨기지 않고 Hermes Alert·Failure Pattern으로 기록한다.
  • 반복 실패가 2회 이상이면 BPR/Tiger가 원인분석을 자동 생성한다.

펄크는 단순 자동화 프로젝트가 아니라, 창업자의 사업 운영 방식을 AI 조직과 데이터 구조로 재설계하는 프로젝트다. 핵심은 에이전트 수가 아니라 Founder DNA · CEO 판단 · PMF 실험 · Workflow 생성 · Native 실행 · Hermes 감시 · Memory 축적 · Tiger 자가개선이 하나의 닫힌 루프로 작동하는 것이다. 그 루프의 뼈대(Phase 1~5)는 이미 동작하며, 이제 Founder-facing 완성과 실사업 적용으로 나아간다.

다음 액션 (압축)

  1. Phase 6 완성 — Chief of Staff Brief 자동생성 → 승인 큐 자동 라우팅 → 메모리 지속화.
  2. CMO 마케팅 자동화를 첫 실사업으로 돌려 실고객 반응 데이터를 넣는다.
  3. Native Orchestration 활성화 + Tiger 상시 루프로 자가개선을 켠다.
  4. Paid Demand가 확인된 워크플로우만 도구화·제품화 후보로 승격한다.

최종 요약 — 펄크의 본질은 "AI로 일을 대신시키는 것"이 아니라 "창업자의 사업 감각과 실행 루프를 회사 운영체계로 만들고, 그 운영체계가 스스로 진화하게 하는 것"이다.

B. 예시 워크플로우

B.1 마케팅 자동화 PMF 실험

  1. Founder: "작은 브랜드의 콘텐츠/마케팅 자동화 문제를 검증한다."
  2. CEO가 가설 생성 → Business Portfolio에 후보 등록.
  3. CMO가 고객 메시지 3종(시간절약·매출개선·운영대행) + 콘텐츠.
  4. CRO가 DM/상담 스크립트.
  5. Risk/QA가 고객 발송 전 확인항목 검토 → Decision Queue "DM 1차 발송 승인".
  6. Founder 승인 → 반응률·상담전환·결제의사 기록.
  7. BPR/Tiger가 문구·고객군·가격·범위 수정 제안 → 반복 요청 시 Tool Request Lab 승격.

B.2 개발 실행 (Native Orchestration)

  1. CPO가 PRD 생성 → CTO가 기술설계·범위, complexity(C) 판정.
  2. pulk CTO가 Work Package로 분해 → main agent 배정.
  3. Native Orchestration이 worktree 격리 → 병렬 phase → verify gate.
  4. 테스트·브라우저 QA 통과해야 완료. Risk/QA가 배포/머지 리스크 확인.
  5. 승인 후 merge → Hermes가 실패 로그·회고 저장.

B.3 Tiger 자가개선

  1. 수집기가 cross-repo 병목 후보 수집 → night-BPR(Claude)이 개선 카드 작성.
  2. /self-improve에서 Founder가 카드 다중선택 → 일괄 승인.
  3. CTO가 repo별 그룹핑 → 병렬 worktree 실행 → verify → merge.
  4. 결과(성공/실패)를 MemoryEntry로 학습 → 다음날 분석 품질 향상.
