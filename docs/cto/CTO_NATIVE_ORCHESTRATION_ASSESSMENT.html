L5 Business OS · CTO 실행 아키텍처 평가

ACR을 빼고, CTO가 Claude Code를 직접 오케스트레이션하는 방향

작성일 2026-06-10 · 근거: 개발 문서만 검토(코드 미분석) · 대상: 사장님 구두 비전

한 줄 결론. 이 방향은 타당하다. 본질은 "ACR을 없애는 것"이 아니라, ACR이 하던 일(격리·검증·에이전트 배정·결과 회수)을 별도 Next.js 시스템 대신 Claude Code의 네이티브 Workflow 기능으로 흡수하는 것이다. 마침 Claude Code Workflow는 사장님이 말한 4가지 — phase별 worktree 격리 · 모델 티어링(opus/sonnet/haiku) · 외부 CLI(codex·agy) 호출 · 중단/재개 — 를 거의 1:1로 이미 지원한다. 단, 검증 게이트·승인 게이트·boundary는 ACR에서 빼더라도 Workflow 안으로 반드시 옮겨야 한다. 빼면 안 되는 건 "시스템"이 아니라 "안전장치"다.

1사장님이 원하는 것 (요약)

CTO가 하는 일 오케스트레이션

  • 전체 PRD를 받아 phase로 분해
  • phase별 worktree 분리로 관리
  • phase 안에서 "이 task는 이 에이전트" 배정
  • 그 배정을 Claude Code CLI에 전달해 실행
  • 토큰 소진 시 회복 대기 → 재개, 중단된 phase 재실행

Claude Code가 하는 일 실행

  • 내부 Workflow 기능으로 task 실행
  • 큰 아키텍처 → Opus
  • 가벼운 개발 → Sonnet/Haiku
  • QA/검증 → Codex 토큰
  • UI/흐름 → Antigravity(AY) 토큰

진짜 목표 핵심

가용한 모든 토큰 풀(Claude·Codex·AY)을 최대치로, 끊김 없이 갈아넣어 개발량을 극대화하고, 토큰이 회복될 때마다 자동으로 다시 투입한다. 사장님은 phase별 진행 상태만 확인한다.

2이 방향이 기존 기획과 충돌하는가?

지난 검토에서 "한 세션이 phase 전체 task를 묶을 때" 4가지 충돌이 있었다. 이번 비전은 그중 2개를 사장님이 직접 해소했다.

기획 원칙상태설명
worktree 격리
30-worktree-policy		 해소됨 사장님이 "phase별 worktree 분리"를 명시 → run마다 격리 원칙 충족. 격리 단위가 task→phase로 격상될 뿐, 격리 자체는 유지.
CTO(brain) ↔ executor 분리
00-global, AGENT_TEAM §1		 해소됨 CTO가 PRD→phase→task→에이전트 배정까지 확정하고 넘김. Claude Code는 "실행"만. 판단은 여전히 CTO. "ACR을 planning brain으로 만들지 않는다" 원칙 유지.
task별 검증 게이트
40-verification "checks passed = Done"		 옮겨야 함 ACR Harness가 강제하던 typecheck/test/boundary를 Workflow의 verify 단계로 이식 필요. 안 하면 "agent says done ≠ Done"으로 후퇴.
승인 게이트 / 위험도 D0–D4
l5-founder-approval-model		 유지해야 함 외부 액션(아웃바운드·결제·배포)은 시스템 구조와 무관하게 살아있어야 함. Workflow 안에서 승인 토큰 게이트로 재현.
boundary / allowedFiles
Harness 11단계		 옮겨야 함 phase worktree + command-guard hook + allowedFiles 검사를 Workflow 진입 전후로 강제. (hook은 .claude/settings.json으로 그대로 따라옴)

결론: 근본 충돌은 0개. 남은 3개는 "ACR이 코드로 강제하던 안전장치를 Workflow 스크립트 안으로 이사"하는 작업일 뿐, 비전과 모순되지 않는다.

3왜 Claude Code Workflow가 ACR의 자연스러운 대체인가

사장님 요구사항과 Claude Code Workflow 기능이 거의 그대로 맞물린다. ACR이 직접 구현하던 것을 네이티브 기능이 대신한다.

사장님 요구ACR이 하던 방식Claude Code 네이티브
phase별 worktree 격리provisionWorktreeForRun (Next.js)agent(..., {isolation:'worktree'}) — 자동 생성·정리
모델 티어링(opus/sonnet/haiku)model-routing.ts + per-phase spawnagent(..., {model:'opus'\|'sonnet'\|'haiku'}) 호출별 지정
Codex / AY 토큰 활용codex·agy CLI를 cold spawnWorkflow 내 Bash로 codex·agy CLI 호출(warm) 또는 agentType
task 병렬 / 의존순서직렬 단일 runner 병목pipeline() / parallel() — 동시 슬롯 자동
중단된 phase 재개큐 재적재 + cwd 수동정리resumeFromRunId — 끝난 agent는 캐시, 중단점부터 재실행
토큰 예산 안에서 최대 투입없음(수동)budget.remaining() 루프 — 예산 소진까지 자동 fan-out
phase 진행 상태만 보기Control Room UI(별도 앱)/workflows 라이브 진행 트리 + log()

핵심 이점 ACR의 가장 큰 병목이던 "직렬 단일 runner + per-phase cold spawn"(속도계획서 P1·P2의 표적)이 Workflow의 pipeline 병렬 + warm 컨텍스트로 구조적으로 사라진다. 별도 launchd 데몬·큐 파일·prepare 409 정리 루프도 함께 제거된다.

역할 매핑 (사장님 비전 → 컴포넌트)

CTO Brain

PRD 분해 · 에이전트 배정 · 검증/승인 정책 결정. 코드 안 씀.

Phase Orchestrator

worktree 생성 · Workflow 기동 · 토큰 회복 대기·재개·재실행. 사장님이 말한 "그 과정"이 여기.

Claude Code Workflow

phase 내 task를 모델·CLI 라우팅으로 실제 실행. 3개 토큰 풀 동시 소비.

5"토큰 최대 투입 + 회복 대기 재개" — 이게 신규 핵심

기존 ACR엔 없던 부분이고, 비전의 알맹이다. 두 층위로 나뉜다.

층위메커니즘비고
Workflow 내부
한 phase 안		 while(budget.total && budget.remaining()>th){ agent(...) } 로 예산 소진까지 task를 계속 fan-out. 동시 슬롯은 자동 캡. "가용 토큰 다 쓴다"를 코드로 보장. 예산은 사장님이 phase별로 지정.
Phase Orchestrator
phase 사이		 rate-limit/quota 소진으로 phase가 멈추면 → ScheduleWakeup로 회복 추정 시점에 깨어나 resumeFromRunId로 중단점부터 재개. "회복되면 다시 쓴다"를 보장. 끝난 agent는 캐시되어 토큰 낭비 없음.
3개 풀 동시
풀 간 부하분산		 Claude 풀이 마르면 같은 phase의 QA/UI task를 Codex·AY 풀로 흘려보내 한 풀이 막혀도 다른 풀로 진행. 총 처리량 = 세 풀의 합. 직렬 ACR로는 불가능했던 지점.

주의 Codex·AY는 Claude Code의 네이티브 agentType이 아니라 외부 CLI다. Workflow 안에서 Bash로 호출하고 결과를 구조화(JSON)로 받아오는 얇은 어댑터가 필요하다. ACR이 이미 codex/agy 헤드리스 호출을 풀어놨으므로(메모리: ACR CLI 완료 현황) 그 호출 규약만 가져오면 된다.

6리스크와 권고

리스크 안전장치 누락

ACR을 걷어내며 검증/boundary/승인 게이트까지 같이 사라지면 품질·안전이 무너진다. → Workflow 템플릿에 verify 단계와 승인 게이트를 기본 내장해 우회 불가하게.

리스크 Workflow는 단일 호스트

ACR launchd처럼 무인 상시가 아니라 세션/turn 기반. 장시간 무인 운전엔 Phase Orchestrator를 launchd/cron으로 띄워 Workflow를 반복 기동하는 얇은 상주 프로세스가 필요.

주의 외부 CLI 결과 구조화

codex/agy의 텍스트 출력을 그대로 신뢰하면 검증이 샌다. outputContract(JSON) 강제 + 실패 시 재시도 어댑터.

주의 결정성

ACR_DETERMINISTIC_PHASES가 보장하던 "built but not wired" 차단(integrate phase)을 Workflow verify 단계에 옮겨 유지.

7최종 판단

✓
방향 자체는 옳다. ACR의 비효율(직렬·cold spawn·별도 앱 운영부담)을 정확히 겨냥했고, Claude Code Workflow가 그 대체를 네이티브로 제공한다. 속도 개선 계획서 P1~P5가 노렸던 것을 "ACR을 고쳐서"가 아니라 "ACR을 흡수해서" 달성한다.
!
"ACR을 뺀다"는 표현은 "시스템을 뺀다"로만 받아들이고, "안전장치를 뺀다"로는 받아들이면 안 된다. 검증·boundary·승인 게이트는 Workflow 안으로 이사시켜 반드시 살린다.
✓
비전의 알맹이(3개 토큰 풀 최대·지속 투입 + 회복 재개)는 ACR엔 없던 신규 가치이고, Workflow의 budget·resumeFromRunId·병렬 + 얇은 Orchestrator로 구현 가능하다.
!
한 방에 ACR을 끄지 말 것. P0 PoC로 월클락·토큰량·품질을 ACR과 수치 비교한 뒤, 동등 이상 확인되면 단계적으로 은퇴시킨다.
