펄크 CTO가 ACR로 코딩하는 전 과정

AI 가상 CTO(최고기술책임자)가 사람 대신 코드를 짜는 방식을 — 작업을 나누는 법부터, 단계별 워크플로우, 모델 배분, 검증, git 브랜치 정리, 그리고 왜 자꾸 병목과 오류가 생기는지까지 — 개발을 모르는 사람도 이해할 수 있게 처음부터 끝까지 풀어 정리했습니다.

작성일 2026-06-09 · 기준 브랜치 claude/purl-cto-acr-docs-qq97pg · 근거: 실제 코드(cto.ts, dev-workflow-spec.ts, model-routing.ts, verifier.ts, acr-client.ts, task-dispatcher.ts, git-acr-cleanup.sh) + 운영 회고 문서 + 최근 git 커밋 40건

⏱️ 30초 요약 (비개발자용)

ACR(Agent Control Room, 에이전트 관제실)은 AI 직원들이 일하는 무인 공장입니다. 그리고 CTO 에이전트는 그 공장의 현장 반장이에요. 누가 "이 기능 만들어줘"라고 지시하면:

  1. 반장(CTO)이 일의 크기를 판단합니다 — "이건 5분짜리 잔손질", "이건 큰 공사" 같은 식으로 7가지 등급으로 분류합니다.
  2. 크기에 맞는 작업 순서표(공정)를 꺼냅니다 — 큰 일은 "조사→설계→테스트→구현→검토→저장"까지 6단계, 작은 일은 2단계.
  3. 각 단계를 실력과 비용이 다른 AI 일꾼(모델)에게 배정합니다 — 어려운 설계는 비싼 고수에게, 단순 작업은 싼 일꾼에게.
  4. 일꾼이 실제로 코드를 짜면, 검수원(verifier)이 결과를 검사하고, 통과하면 다음 단계로 넘깁니다.
  5. 위험한 작업(고객 결제·배포 등)은 사람(파운더)의 승인을 받고 진행합니다.

문제는, 이 공장이 한동안 거의 멈춰 있었다는 점입니다. 작은 일도 6단계를 다 돌리고, 빈 결과를 실패로 오인해 재시도하고, 안전장치가 내부 작업까지 막고, 다 끝난 임시 작업 폴더(git 브랜치)가 수백 개씩 쌓였습니다. 이 문서는 그 전 과정과 8가지 병목, 그리고 최근 고친 내용(B1~B5)을 모두 기록합니다.

1. ACR과 CTO가 뭔가요? 개념

코드를 모르는 분을 위해 먼저 등장인물을 정리합니다. 이 시스템에는 사람 직원이 거의 없고, 대부분 AI 역할(에이전트)이 일합니다.

🏭 ACR (Agent Control Room)

AI 일꾼들이 실제로 코드를 짜는 무인 공장 / 관제실. 작업 지시서를 받으면 단계별로 AI를 돌려 코드를 만들고, 결과를 기록합니다. 펄크 본체(L5)와는 인터넷(HTTP API)으로 연결된 별도 시스템입니다.

👷 CTO 에이전트

공장에 일을 넘기기 전에 작업을 설계하는 현장 반장. "이 일은 얼마나 큰가, 몇 단계로 쪼갤까, 누구에게 맡길까, 위험한가"를 판단합니다. 코드 위치: services/agent-runtime/src/agents/cto.ts

📋 L5 (펄크 본체)

회사 운영 콘솔. 파운더의 지시를 받아 "할 일(Task)" 목록을 만들고 대기열에 넣습니다. CTO는 이 본체의 한 부서장입니다.

🚚 Hermes / Dispatcher

대기열의 할 일을 꺼내 담당 부서장(CTO 등)에게 배달하는 배차 담당. 코드: services/hermes-runtime/.../task-dispatcher.ts

🍔 비유

패스트푸드 주방을 떠올려 보세요. 손님 주문(파운더 지시)이 들어오면 → 배차 담당이 주문표를 주방장(CTO)에게 줍니다 → 주방장은 "햄버거 하나는 2분, 케이터링 100인분은 큰 공정"이라 판단하고 레시피(공정표)를 정합니다 → 각 조리 단계를 알바생(AI 모델)에게 나눠줍니다 → 검수원이 맛을 보고(verifier) → 통과하면 손님께 나갑니다. ACR은 바로 이 주방 전체입니다.

2. 전체 워크플로우 한눈에 전체 그림

지시 한 줄이 코드가 되어 저장되기까지 거치는 7개 큰 단계입니다. 각 단계는 아래 섹션에서 하나씩 자세히 풉니다.

① 할 일 대기열 (L5)→ ② 배차 (Dispatcher)→ ③ CTO 분류→ ④ 공정·모델·위험도 결정→ ⑤ ACR로 지시서 전달→ ⑥ 단계별 실행+검증→ ⑦ 브랜치 머지·정리
단계담당하는 일핵심 코드
① 대기L5 본체파운더 지시를 "할 일(Task)"로 만들어 queued 상태로 대기열에 넣음NocoBase
② 배차Dispatcher승인 불필요 + 대기중인 할 일만 꺼내 담당 에이전트에게 전달task-dispatcher.ts
③ 분류CTO제목·설명을 보고 7등급 중 하나로 자동 분류 (AI 호출 없이 규칙으로)classifyTask()
④ 설계CTO등급별 공정표 꺼냄 → 각 단계에 모델 배정 → 위험도·승인 게이트 계산dev-workflow-spec.ts, model-routing.ts
⑤ 전달CTO→ACR"지시서(ACRIntent)"를 만들어 ACR 공장에 HTTP로 보냄. 할 일은 running으로 표시acr-intent.ts, acr-client.ts
⑥ 실행ACR 공장단계마다 AI(claude/codex/gemini)를 돌려 코드 생성 → 검수원이 합격/불합격 판정 → 다음 단계verifier.ts
⑦ 정리git 스크립트임시 작업 폴더(acr/... 브랜치)를 main에 합치고, 끝난 건 삭제git-acr-cleanup.sh
💡 핵심 한 줄

CTO는 직접 코딩하지 않습니다. CTO가 하는 일은 "어떻게 만들지 설계도와 작업지시서를 짜서 공장에 넘기는 것"이고, 실제 코딩은 ACR 공장 안의 AI 일꾼들이 합니다. 그래서 속도와 오류는 코딩 실력이 아니라, 일을 어떻게 쪼개고 배분하고 관리하느냐에서 거의 다 결정됩니다.

3. 1단계 — 작업 분류 (7등급) CTO 권한

모든 것의 시작입니다. CTO는 할 일의 제목과 설명만 보고 AI를 호출하지 않고 정해진 규칙으로 7등급 중 하나를 정합니다. (예전엔 매번 AI에게 물어봤는데, 그게 느림의 원인이라 규칙으로 바꿨습니다 — B1 참고.) 이 등급이 이후 모든 것(몇 단계로 쪼갤지, 어떤 모델을 쓸지)을 결정합니다.

등급뜻예시공정 수
TINY진짜 사소한 일오타 수정, 한 줄 변경, 상수 추가, 이름 바꾸기(rename)2단계
SMALL_FIX작은 버그 수정·단일 컴포넌트카드 1개, 버튼, 엔드포인트 하나, 작은 버그4단계
FEATURE일반적인 새 기능새 화면, 여러 파일에 걸친 기능6단계
BIG_CHANGE큰 변경 (위험·광범위)200줄+ 변경, 모듈 3개+ 영향, 스키마/공개 API 변경6~7단계 (RFC 추가)
OPS운영·인프라 작업배포, 마이그레이션, launchd, 롤백, 백업4단계
RESEARCH조사·비교만"X와 Y 비교", 기술 survey, 탐색1단계
REFACTOR구조 개선(기능 동일)리팩터링, 리팩토링4단계

분류는 어떻게 결정되나 (판단 순서)

  1. 키워드 우선: 제목에 "리팩터/리팩토링"→REFACTOR, "조사/비교/survey"→RESEARCH, "배포/마이그레이션/롤백/운영"→OPS 처럼 명확한 단어가 있으면 바로 결정.
  2. 복잡도 점수(escalation, 5개 신호): ① 변경 줄 200 초과 ② 영향 모듈 3개 초과 ③ 새 외부 의존성 ④ 스키마/DB 변경 ⑤ 공개 API 깨짐. 이 중 3개 이상이면 등급을 한 칸 올림(SMALL_FIX→FEATURE→BIG_CHANGE).
  3. TINY 판정: "오타/typo/한 줄/함수 하나/rename/trivial" 같은 신호 + 예상 30줄 이하 + 모듈 1개 이하 + 위 복잡도 신호가 하나도 없을 때만.
  4. 단일 컴포넌트 강등: FEATURE로 보였지만 "card/panel/badge/modal/endpoint/컴포넌트" 같은 단일 요소 키워드 + 복잡도 2 미만이면 → SMALL_FIX로 내림. (작은 UI를 6단계로 과설계하지 않으려는 장치 — B2)
🧰 비유

철물점 사장님이 손님 말만 듣고 "이건 못 몇 개면 되는 잔손질", "이건 인테리어 공사"라고 즉석에서 판단하는 것과 같습니다. 매번 본사에 전화해 묻지 않고(=AI 호출 안 함) 경험 규칙으로 빠르게 정하는 게 핵심입니다.

4. 2단계 — 등급별 공정(Phase) 전부 SOP

등급이 정해지면, 정해진 표준 작업순서(SOP)가 자동으로 나옵니다. 각 단계(phase)는 ① 한국어 이름 ② 담당 런타임 ③ 읽기전용 여부 ④ 합격 기준 ⑤ 직전 단계 의존성을 가집니다. 아래는 7개 등급의 모든 공정입니다.

TINY — 2단계

구현→커밋

진짜 사소한 일은 조사·스펙·리뷰를 모두 생략. 수 초 안에 끝남.

SMALL_FIX — 4단계

재현 테스트→버그 수정→회귀 확인→커밋

버그를 먼저 테스트로 재현 → 고침 → 다른 데 안 깨졌나 확인 → 저장.

FEATURE — 6단계 (표준 풀코스)

오픈소스 조사→스펙 작성→실패 테스트→구현→리뷰→커밋

테스트를 먼저 써서 일부러 실패시키고(red), 구현으로 통과시키는(green) TDD 방식.

BIG_CHANGE — 7단계 (RFC 추가)

RFC 작성→스펙→실패 테스트→구현→리뷰→커밋

큰 변경은 맨 앞에 "왜·어떻게 바꿀지" 설계 제안서(RFC)를 한 단계 더 둠.

OPS — 4단계

백업·롤백 계획→운영 실행→스모크 테스트→커밋

운영 작업은 사고에 대비해 백업/되돌리기 계획을 먼저 세움.

RESEARCH — 1단계

조사 및 비교

코드 변경 없이 조사 결과만 산출.

REFACTOR — 4단계

회귀 green 확보→리팩터링→회귀 재확인→커밋

기능을 안 바꾸므로, 고치기 전·후로 "동작 그대로인지" 두 번 확인.

각 단계가 가진 정보

모든 공정 단계는 내부적으로 다음 정보를 담은 "작업 카드"입니다(코드상 DevPhaseTemplate):

  • kind: 단계 종류 — spec, test, implement, review, commit, repro, fix, regress, research, rfc, refactor, backup, smoke 중 하나
  • name: 운영자가 보는 한국어 이름 (예: "실패 테스트 작성")
  • runtime: 어떤 AI 도구로 돌릴지 (claude 또는 codex)
  • read_only: 이 단계가 파일을 고치지 않고 읽기만 하는지 (읽기전용이면 위험도 D2 이하로 강제)
  • acceptance_criteria: 합격 기준 목록 (예: 구현 단계 → "직전 실패 테스트가 통과한다(green), 기존 테스트가 회귀 없이 통과한다")
  • verifier_hint: 검수원이 무엇을 봐야 하는지 힌트
  • dependsOn: 반드시 끝나야 하는 직전 단계

안전장치 — 공정 검증(validateDevWorkflowPhases)

만약 AI가 공정을 직접 생성하는 모드라면, CTO는 그 결과가 SOP와 정확히 맞는지 검사합니다: 단계 수가 맞는가 / 순서가 맞는가 / 의존성이 맞는가 / 빈 칸이 없는가. 두 번 실패하면 AI를 포기하고 정해진 템플릿(buildDeterministicDevPhases)을 그대로 씁니다. 그래서 공장은 항상 형식이 올바른 지시서를 받습니다.

5. 3단계 — 모델 배분 (T1/T2/T3) 비용 vs 품질

각 공정 단계를 실력·비용이 다른 AI 모델에 배정합니다. 비싼 고수에게 모든 걸 맡기면 돈·쿼터가 빨리 닳고, 싼 일꾼에게 어려운 설계를 맡기면 품질이 떨어집니다. 그래서 티어(tier)로 나눕니다. (코드: model-routing.ts)

T1
claude-opus
최상위 추론(고수)
런타임: claude
T2
gpt-4o
균형 구현(중간)
런타임: codex
T3
claude-haiku
경량·저비용(빠름)
런타임: antigravity

단계 종류별 기본 배정

티어맡는 단계이유
T1 (고수)rfc, research, spec, review설계·검토는 머리를 많이 써야 함
T2 (중간)test, implement, fix, refactor, repro, backup실제 구현은 균형형으로
T3 (경량)smoke, regress, commit기계적·반복 작업은 싼 모델로

등급별 예외 (override)

  • TINY: 빨리 끝내려고 두 단계 모두 T1(claude). 테스트상 단계당 ~13초.
  • SMALL_FIX: 비용 절감 — fix·repro를 T3로 내림.
  • BIG_CHANGE: 품질 사수 — implement·test를 T1로 올림.
  • OPS: 기계적이지만 위험 — backup을 T3로.
✅ B5 — 쿼터 인지 라우팅

모델마다 하루 사용 한도(쿼터)가 있습니다. 예전엔 codex 쿼터가 바닥나도 계속 codex로 일을 보내 빈 결과 → 재시도가 반복됐습니다. 지금은 배정 전에 ACR의 quota-tracker.json을 읽어, 소진된 티어는 건너뛰고 사용 가능한 다음 티어로 자동 폴백합니다. (T1→T2→T3, 혹은 T2→T3→T1 순) 단, 핵심 설계인 T1 단계는 model_locked로 잠가 함부로 강등하지 않습니다.

6. 4단계 — 위험도(D1~D5)와 승인 게이트 안전

모든 작업에는 위험도가 붙고(프로젝트 규칙 4·5), 위험도에 따라 사람의 승인이 필요한지가 갈립니다. CTO가 자동으로 계산합니다(gateFromRisk()).

✅ B4 — D3 사전판단

D3 판정을 매번 AI에게 묻던 걸, 명확한 경우는 규칙으로 즉답하게 했습니다. "매출/결제/고객메시지/배포/마이그레이션/환불/계약/법률" 단어가 있으면 → 즉시 사람 승인으로 격상(AI 호출 0). "조사/리뷰/리팩터/내부유틸"이면 → 즉시 통과. 애매한 회색지대만 AI에게 넘깁니다. 약 70%의 판정에서 AI 호출이 사라졌습니다.

7. 5단계 — ACR로 지시서 전달 & 비동기 실행 전달

CTO는 위 모든 결정을 모아 하나의 지시서(ACRIntent)로 포장해 ACR 공장에 HTTP로 보냅니다.

지시서(ACRIntent)에 담기는 것

{
  l5_task_id:   "할 일 고유번호"
  task_title:   "작업 제목"
  phases: [ {                    ← 순서가 있는 공정 카드들
      name:                "실패 테스트 작성"
      runtime:             "codex"          ← 어느 AI 도구
      prompt_packet:       "[test] ... 작업 지시 + 합격기준 + 힌트"
      expected_output:     "합격 기준들 (세미콜론 구분)"
      risk_level:          "D2"
      release_gate_type:   "none"
      l5_approval_required: false
      auto_execute:         true
      model_locked:         false           ← 쿼터로 강등 금지 여부
  }, ... ]
  project_path: "공장이 작업할 폴더 경로"
  l5_approved:  true                         ← L5 승인 게이트 통과 여부
}

전달 과정

  1. 프로젝트 등록: 처음이면 POST /api/projects로 ACR에 프로젝트를 만듦(부트스트랩).
  2. 지시서 전송: POST /api/workbench/dispatch로 지시서를 보냄.
  3. 할 일은 "running"으로: 공장이 여러 분에 걸쳐 비동기로 단계를 돌리므로, 배차 담당은 할 일을 done이 아니라 running으로 두고 빠집니다. 관제실 화면이 진행 상황을 실시간으로 보여줄 수 있게요. 모든 단계가 끝나면 콜백(taskCallback)이 done으로 마감합니다.
⚠️ 여기가 함정이었다

예전엔 배차 담당이 CTO 할 일을 곧바로 done으로 표시해버려서, 실제로는 공장에서 돌고 있는 작업들이 화면에서 전부 사라졌습니다("진행 중인 일이 안 보임"). 지금은 running으로 두고, 멈춘 작업은 별도 감지기(stalled-task-detector)가 잡습니다.

8. 6단계 — 검증(Verifier) 검수원

각 단계 실행이 끝나면 검수원이 "정말 합격 기준을 만족했나"를 봅니다. 핵심은 AI 없이 결정적으로(deterministic) 판정한다는 것 — 빠르고 일관됩니다(verifyCTOPhaseDeterministic). 검수원이 보는 것: 종료 코드(exit code), 로그 끝부분, git diff 통계(변경 파일 수).

상황판정재시도?
종료 코드가 0이 아님 (오류로 끝남)fail예
로그에 [ERROR], Traceback, panic:, fatal: 등fail예
코드를 만들어야 하는 단계인데 변경 파일이 0개fail예
변경도 없고 변경이 필요한지도 애매inconclusive아니오
정상 종료 + 오류 없음 + (변경 있음 or 읽기전용)pass아니오
✅ B3 — 빈 결과 오탐 차단

커밋·리뷰·조사 같은 단계는 원래 코드를 안 만드는 게 정상입니다(마크다운 요약만 출력). 예전 검수원은 "변경 파일 0개 = 실패"로 오인해 멀쩡한 단계를 2번씩 재시도해 토큰을 낭비했습니다. 지금은 합격 기준 문구에 "구현/수정/작성/코드" 같은 코드 생산 신호가 있을 때만 "변경 0개=실패"로 보고, 그렇지 않으면 정상 통과시킵니다.

9. 7단계 — git 브랜치 생성과 정리 정리

ACR은 단계를 실행할 때마다 임시 작업 폴더(git 브랜치)를 만듭니다. 이름 규칙:

acr/l5-<프로젝트UUID>-task-<단계번호>-<날짜>
예) acr/l5-cf465c42-...-task-4-20260604-2007

커밋 메시지에서도 보입니다: ACR phase: 스펙 작성 [acr/l5-...], ACR phase: 실패 테스트 작성 [...], ACR phase: 구현 [...], ACR merge: [L5] ... [...]. 즉 한 작업이 스펙→테스트→구현→머지 단계마다 별도 브랜치/커밋을 남깁니다.

⚠️ 병목 — 브랜치 폭증

ACR이 머지 후 브랜치를 지우지 않아 로컬·원격에 수백 개가 쌓였습니다. 2026-06-05 기준 로컬 291개 · 원격 25개. 근본 해결은 "ACR이 머지 후 스스로 삭제"하는 것이고, 그때까지는 청소 스크립트가 안전망입니다.

청소 스크립트 — scripts/git-acr-cleanup.sh

다음 조건을 모두 만족하는 acr/* 브랜치만 지웁니다: ① 이미 main에 머지됨 ② 7일 이상 지남(AGE_DAYS) ③ 보호 대상 아님(main, cmo/, feat/, omc/, wip/) ④ 현재 체크아웃되지 않음.

bash scripts/git-acr-cleanup.sh            # 미리보기(삭제 안 함)
bash scripts/git-acr-cleanup.sh --apply    # 실제 삭제
AGE_DAYS=3 bash scripts/git-acr-cleanup.sh --apply

로컬은 git branch -D, 원격은 git push origin --delete로 정리합니다.

10. 왜 자꾸 병목·오류가 생기나 — 8가지 핵심 진단

이 부분이 질문의 핵심입니다. CMO 영상룸 프로젝트에서 158개 공정을 끝까지 돌리며 실제로 겪은 병목입니다. 운영 회고의 한 줄이 모든 걸 요약합니다:

"처음엔 정체·오탐·고아·손상으로 거의 안 움직였고, 병목을 하나씩 제거하니 +5/27분 → +21/27분(4배 가속)으로 빨라졌다. 즉 속도는 작업 난이도가 아니라 오케스트레이션·게이트·모델 배분에서 결정됐다."

1과도한 공정 분해 — 최대 낭비

영향 ★★★

증상: CTO가 28개 기능을 전부 FEATURE(6단계)로 분류 → 28×6 = 158개 공정. 그런데 조사·스펙·리뷰·커밋 4개는 코드를 안 만들면서 토큰만 씁니다. 카드 1개 추가에도 풀코스 6단계가 돌았습니다.
왜: 분류 규칙이 너무 거칠어 작은 UI와 복잡한 기능을 똑같이 취급. SOP는 큰일엔 맞지만 작은 일엔 과설계.

2콜드스타트 + 컨텍스트 재사용 0

영향 ★★

증상: 공정마다 새 AI 세션이 코드베이스를 처음부터 다시 읽음. claude 콜드스타트만 수십 초. 158번 반복되면 막대한 누적 낭비.
왜: 따뜻한 세션 재사용(--resume)이 꺼져 있었음(ACR_WARM_SESSIONS 미설정).

3빈 결과 공정이 "실패"로 막힘

영향 ★★★

증상: 커밋·리뷰·조사 단계는 파일 변경이 0 → 검수원이 "빈 산출물"로 보고 review_blocked → 작업이 영영 완료 못 됨. 게다가 2회 재시도로 토큰이 2~3배.
왜: 검수원이 "정상적인 무(無)코드 단계"와 "진짜 실패"를 구분 못 함.

4안전 게이트 3종의 내부 코딩 오탐

영향 ★★★

증상: ① 위험명령 탐지기가 프롬프트에 token/secret/deploy/migrate 단어만 있어도 차단 ② 위험 분류기가 내부 D2 코딩을 D4(사람 승인)로 격상 ③ 게이트가 막을 때 작업을 running으로 방치 → 고아 작업이 동시성 슬롯을 막아 데드락.
왜: 게이트는 "외부 위험 작업(고객 메시지·결제·배포)"용인데 격리된 내부 코딩에도 적용됨. L5가 이미 승인한 작업에 중복 게이트.

5오케스트레이션이 작업을 잃고 정체

영향 ★★★

증상(반복됨): ACR이 인메모리 락(planDrainLock) + 긴 HTTP 1회로 작업을 직렬 실행 → 연결 끊김/행(hang) 시 락이 안 풀려 전체가 멈춤. acr-web을 재시작해야만 풀리고, 재시작하면 진행 중이던 공정이 폐기·재실행(토큰 낭비). 약 6분마다 정체→재시작이 반복됐고, 17분짜리 고아 작업도 발생.
왜: 인메모리 락 + inline-HTTP + 행 감지/타임아웃 부재. 분산 비동기 작업엔 부적합한 구조.

6비원자적 JSON 쓰기 → 파일 손상

영향 ★★

증상: 여러 작업이 동시에 같은 JSON 파일(execution-logs.json 등)에 쓰면서 내용이 뒤섞여 "Extra data after JSON" 손상 → 그 파일을 읽는 모든 후속 작업이 연쇄 실패.
왜: 일반 파일 쓰기는 원자적이지 않아 동시 쓰기에 깨짐. 임시파일+이름변경(temp+rename) 방식을 안 씀.

7모델/쿼터 미스매치 → 죽은 에이전트로 발송

영향 ★★★

증상: codex(T2) 쿼터 소진, agy가 이미 소진된 모델("Claude Sonnet 4.6 Thinking")로 고정돼 빈 출력. 라우팅이 쿼터를 무시하고 죽은 에이전트로 계속 발송 → 폴백·재시도 낭비.
왜: 쿼터 추적 데이터(quota-tracker.json)는 ACR에 있었지만 CTO 라우터가 한 번도 참조하지 않음. 가용성 가정하고 맹목 배정.

8병렬 worktree의 통합 충돌

영향 ★

증상: 속도를 위해 4개 worktree를 병렬로 돌렸지만, 공유 파일(Sidebar, 라우터, package.json)을 각자 독립 수정 → 마지막에 병합 충돌을 수동 해결.
왜: 병렬 작업이 같은 통합 지점을 동시에 건드림. 공유 파일 경계를 미리 정하지 않음.

한 줄 결론

병목의 공통 뿌리는 "코딩이 어려워서"가 아니라, 일을 너무 잘게 쪼개고(1), 매번 처음부터 시작하고(2), 정상 결과를 실패로 오인하고(3), 안전장치가 과민하고(4), 작업 관리 구조가 약하고(5·6), 가용 자원을 안 보고 배정하는(7) — 오케스트레이션·게이트·자원관리 문제였습니다.

13. 아직 안 고친 것 — 다음 숙제 미해결

B1~B5는 "분류·검증·라우팅" 같은 의사결정 로직을 고쳤습니다. 하지만 더 깊은 구조적 문제는 다음 단계 숙제로 남아 있습니다.

① 인메모리 락 → 잡 큐로 (병목 #5)

지금은 정체되면 자동 재시작으로 때우는 임시 처방. 근본 해결은 파일/DB 기반 잡 큐 + 워커 구조 — dispatch는 큐에 넣고 즉시 반환, 워커가 처리, 행은 하트비트·타임아웃으로 정리(재시작 불필요).

② 브랜치 자동 삭제 (병목 git)

청소 스크립트는 안전망일 뿐. 근본은 ACR이 머지 직후 자기 브랜치를 스스로 삭제하도록 만드는 것.

③ 게이트 적용 범위 축소 (병목 #4)

안전 게이트는 D4/D5 외부·결제 작업에만 적용하고, 내부 D2 코딩은 기본적으로 게이트를 건너뛰게. (self-mod 보호만 유지)

④ 병렬 통합 지점 선(先)셋업 (병목 #8)

공유 컴포넌트·라우터·스키마를 먼저 한 번 직렬로 셋업한 뒤 기능별 병렬. 또는 기능별 파일 경계를 강하게 잡아 충돌 면적 축소.
